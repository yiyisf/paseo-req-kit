# 项目定制与运行规则

## 每个需求一个 worktree 工作区

在 Paseo 中为每个需求新建工作区：**New workspace** → 选择项目 → **Isolation** 选 **New worktree** → 起点选主分支，然后在这个工作区的对话里输入 `/req`。

- 流水线在这个工作区自己的目录和分支上运行、提交，不影响项目主目录。
- 同一个目录一次只能运行一条流水线；用了 worktree，几个需求可以同时进行。
- 在主目录发起时，`/req` 会先建议改用 worktree；使用者坚持的话，它会新建 `feature/<功能目录名>` 分支再继续。

**分支规则**：流水线把启动时检出的分支作为本次需求的工作分支，所有步骤都提交到这里，不切换、不新建分支。它拒绝在默认分支（`main`、`master` 或 `origin/HEAD` 指向的分支）或 detached HEAD 上启动；续跑时分支变了也会拒绝。

## 档位

| 档位 | 适用 | 访谈 | 流程 |
| --- | --- | --- | --- |
| 快速（`quick`） | 小改动：文案、样式、配置项、字段显示等，不涉及数据结构、权限、对外接口 | 只问要改什么、改成什么样、不改什么、验收标准 | 审核、评审、缺陷修复各一轮；不做服务启动验证；产物从简 |
| 标准（`standard`） | 其他情况 | 完整访谈 | 审核最多 2 轮、评审最多 3 轮、缺陷修复最多 3 轮 |

`/req` 会根据需求推荐档位，用户确认后写进 spec（`- 档位：快速`）。流水线按以下顺序决定档位：`--profile` 参数 → 续跑时沿用上次的档位 → spec 中的档位 → 配置中的 `defaultProfile`。各档的轮数和是否做服务启动验证可以在配置的 `profiles` 中调整。

## 执行方式：连续、分阶段、只做研发

第 3–11 步分为两个阶段：**研发**（方案设计 → 方案审核 ⇄ 修订 → 实现 → 代码评审 ⇄ 修复 → 提测说明）和**测试验证**（服务启动 → 功能验证 → 缺陷处理），之后是完成报告。研发阶段的最后一步写提测说明 `handoff.md`：改了什么、怎么跑起来、自测结果、建议重点测试、已知问题、测试前的准备。

| 执行方式 | 研发完成时 | 适合 |
| --- | --- | --- |
| 连续（`continuous`，默认） | 直接进入测试验证，与 1.7 之前一致 | 本地就能验证的项目 |
| 分阶段（`gated`） | 停下来通知"研发完成，可以提测"；由人说"开始测试验证"，或到 `--verify-at` 预约的时间开始 | 有专门测试、需要先部署测试环境 |
| 只做研发（`develop-only`） | 写研发报告后结束；验收时按提测说明人工测试。之后仍可用 `--phase verify` 让流水线验证 | 测试必须由人完成 |

来源，后者覆盖前者：配置 `phases.mode` → spec 头部 `- 执行方式：分阶段` → 启动参数 `--phases`。有测试团队的项目建议在项目配置中写：

```json
{
  "phases": {
    "mode": "gated",
    "verify": {
      "environment": "deployed",
      "agents": { "reviewer": { "paseoProfile": "测试" } },
      "defects": "handback"
    }
  }
}
```

| `phases.verify` 中的配置 | 默认 | 作用 |
| --- | --- | --- |
| `environment` | `"local"` | `"deployed"`：不在本地启动服务，对已部署的测试环境验证。功能目录中需要 `test-env.md`（地址、怎么确认版本、账号和口令从哪里取、可用的测试数据；不写口令本身），没有就拒绝开始。开始测试时可用 `--verify-env` 临时指定 |
| `agents` | `{}` | 测试阶段的步骤（服务启动、功能验证、缺陷修复、复验）用的 agent，格式同顶层 `agents`，可用 `paseoProfile`；没写的角色用顶层的。完成报告仍用顶层的 builder |
| `defects` | `"fix"` | `"fix"`：当场修复并复验；`"handback"`：只记录，在 `changes.md` 追加"测试验证退回"一节，回到研发阶段从方案设计开始修复，经过代码评审、重写提测说明后再提测（分阶段时再次停在闸口），最多退回档位的缺陷修复轮数次；`"report"`：只记录，直接出报告。开始测试时可用 `--defects` 临时指定 |
| `serviceStart` | `null` | 测试阶段是否做服务启动验证；`null` 按档位。`deployed` 时不做 |

**谁可以开始测试验证**：发起的对话；需求在自动新建的工作区中（`--worktree`）时，同一仓库任何工作区中的对话也可以（研发阶段仍只能从原对话操作），之后的通知转到那个对话。测试阶段开始前需求说明改过的，先回到研发阶段处理变化。用时与用量在状态和完成报告中按阶段分别统计。见 ADR 0022。

## 进展通知

除了"需要需求方决定""等待批准""中断""完成"这几种通知，流水线默认还会在三个节点各发一句进展：技术方案已经确定、开始写代码；代码通过检查、开始验证；验证发现问题、正在修复。续跑时不会重复发送。不需要的话，在配置中设 `"notifyMilestones": false`。

**同时发到企业 IM**：配置 `notifiers` 后，这些通知还会交给你实现的通知模块，例如转发到企业内部 IM。`notifiers` 只能写在本机或团队配置中（项目配置中的会被忽略）。做法见 [安装与升级](安装与升级.md) 第 12 节，事件格式见 `contracts/notifier-event.md`。

## 运行时文件

运行时的文件都在功能目录下的 `.pipeline/` 中，不会被提交：

- `state.json`：当前状态、档位、工作分支、每个步骤的 agent ID 和结果、历次尝试的记录
- `results/<步骤>.json`：每个步骤的结果文件
- `pipeline.log`：运行日志，包括使用了哪些配置文件、发出的每一条通知和每次自动重试

**用时与用量**：每个步骤记录 agent 的起止时间和 agent 报告的 token 用量、费用（有的 agent 不报告）。查看进度（`req status`）、需求总览（`req list`）和完成报告都会显示合计。评审小组的成员并行运行，所以"agent 合计用时"可能比实际经过的时间长。

## 按项目定制

本机配置（`~/.req-kit/config.json`）对所有项目生效。各项目可以在仓库里放自己的定制，随代码一起提交，团队共享。最简单的做法是在项目根目录的对话中运行 `/req-setup`，它会生成前两份文件并实际运行验证命令：

```text
<仓库根目录>/
├── .requirement-pipeline.json          覆盖本机配置中的项
└── .requirement-pipeline/
    ├── project-notes.md                追加到每个步骤的提示词；/req 访谈前也会读
    ├── verify.md                       验证方法；追加到实现、修复、服务启动、验证、复验步骤
    └── steps/
        └── <步骤>.md                   只追加到某一步，例如 verify.md
```

**`.requirement-pipeline.json`** 可以设置除 `daemonUrl`、`daemonPasswordEnv`、`teamConfig` 以外的所有项（这几项描述的是本机，写了会被忽略，并在日志和 `/req-doctor` 中提示）。例如这个项目默认走快速档、实现用另一个模型：

```json
{
  "defaultProfile": "quick",
  "agents": { "builder": { "provider": "claude/<模型 ID>", "modeId": "bypassPermissions" } },
  "profiles": { "standard": { "rounds": { "codeReview": 2 } } }
}
```

`agents` 按角色整体替换；`profiles`、`stepTimeoutMinutes` 按项合并。

**`project-notes.md`** 写这个项目的约定，例如：

```markdown
- 包管理用 pnpm，不要用 npm。
- 不要改动 legacy/ 目录。
- 数据库变更必须写成 migrations/ 下的迁移脚本。
```

**`verify.md`** 写这个项目怎么安装依赖、启动服务、运行测试、准备测试数据，命令要实际运行过。结构建议见 `contracts/verify.md`。步骤 agent 发现它过时或不准确时，会在 `service-start.md` 或 `verification.md` 的"建议写入 verify.md 的内容"一节给出实际可行的做法；再次运行 `/req-setup` 会参考这些建议更新它。项目的构建文件改过而 `verify.md` 没有更新时，`/req-doctor` 会提醒。

**`steps/<步骤>.md`** 的文件名用步骤 ID：`design`、`design_review`、`design_revise`、`implement`、`code_review`、`review_fix`、`service_start`、`verify`、`defect_fix`、`reverify`、`report`。例如 `steps/verify.md` 写"端到端测试用 `pnpm e2e` 运行，测试账号见 docs/test-accounts.md"。

这些内容追加在步骤任务之后，并注明"与通用要求冲突时以项目说明为准"，但"如实报告"和安全要求始终有效。

**统一修改某一步的提示词**：在 `~/.req-kit/prompts.local/` 中放入与 `engine/prompts/` 中同名的文件，就会替换随版本发布的那一篇。升级只替换版本目录，`prompts.local/` 不受影响；但新版本对同名提示词的改进也不会生效，升级时请对比。这是最后的手段：能写进项目说明、配置或测试的，优先写在那里。

## paseo.json：环境准备和由 Paseo 管理的服务（推荐）

`paseo.json` 是 Paseo 自己的项目文件，放在仓库根目录并提交。`/req-setup` 可以生成它：

```json
{
  "worktree": { "setup": ["npm ci", "node scripts/paseo/copy-local-files.mjs .env"] },
  "scripts": {
    "test": { "command": "npm test" },
    "web": { "type": "service", "command": "node scripts/paseo/with-port.mjs npm run dev -- --port {PORT}" }
  }
}
```

`paseo.json` 是团队共用的，而 Paseo 在各系统上用不同的 shell 执行它的命令（macOS/Linux：bash 和 sh；Windows：准备命令用 PowerShell，带 `-ExecutionPolicy Bypass`，不受执行策略限制；脚本和服务用 cmd.exe）。所以 `/req-setup` 只写各系统一样的命令，用到环境变量的地方交给它写进项目的两个小脚本：`scripts/paseo/copy-local-files.mjs`（从来源目录复制不提交的本地文件，没有就跳过）和 `scripts/paseo/with-port.mjs`（把 `{PORT}` 换成 Paseo 分配的端口，并设置 `PORT`）。手写 `$PASEO_PORT`、`%PASEO_PORT%`、`cp`、`Copy-Item` 这类只在某个系统上能用的命令时，`/req-doctor` 会指出：在本机上会失败的标为⚠，只是换系统会失败的给出提示。

- `worktree.setup`：Paseo 新建 worktree 工作区时自动执行，新需求的工作区一建好就装好了依赖、带上了本地配置。
- `"type": "service"` 的脚本：流水线在服务启动验证、功能验证、缺陷修复和复验之前，通过 Paseo 带着当前代码重启它们，把地址（`http://web--<分支>--<项目>.localhost:6767` 这样的代理地址）交给步骤 agent，验证结束后停止。Paseo 为每个工作区分配独立端口，几个需求同时验证不会冲突，服务必须监听 Paseo 分配的端口（环境变量 `PASEO_PORT`，用 `with-port.mjs` 传给程序）。
- 服务没有启动成功时，最后的输出写到功能目录的 `.pipeline/services/<服务名>.log`，交给步骤 agent 查原因。
- 只有从 Paseo 对话启动的流水线才会这样做（需要知道是哪个工作区）。不想用时在配置中设 `"paseoServices": "off"`，步骤 agent 会像以前一样自己启动服务。`serviceReadySeconds`（默认 120）是等待服务就绪的时间。
- 在 Paseo 设置中打开 **Enable Paseo tools** 后，步骤 agent 改完代码还可以自己重启这些服务。
- 写错时服务起不来，流水线会改由步骤 agent 自己启动服务，不会中断。
- PowerShell 被完全禁用（不只是执行策略）的 Windows 机器上，`worktree.setup` 无法执行；新工作区不会自动装依赖，步骤 agent 会按验证方法自己准备。

## 额度提醒

开始前，流水线读取 Paseo 的用量信息（需要 Paseo 能读到对应 agent 的订阅用量）。所用 agent 的某个额度窗口用到 `quotaWarnPercent`（默认 85）以上时，在对话里提醒一次，流水线照常进行；用完时遇到限流会自动等待重试。设为 0 关闭提醒。

## 并行编排：确认前审阅、方案提案、浏览器验证

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `specReview` | `"standard"` | 请需求方确认之前，由 reviewer 在后台独立审阅需求说明草稿，问题写进 `spec-review.md`。`"always"` 快速档也做，`"off"` 关闭 |
| `designProposals` | 关闭 | `{"enabled": true}` 后，标准档的方案设计之前由几个 agent 并行各提一份方案（`design-proposals/`），方案设计比较后决定。`members` 不写时用 builder 和 reviewer，也可以像评审小组一样列出成员（可用 `paseoProfile`）。需求变更后的增量继续不做 |
| `browserVerify` | `"auto"` | 步骤 agent 有 Paseo 浏览器工具（Paseo 设置中打开 Enable Paseo tools 和浏览器工具，桌面端在线）时，功能验证、缺陷修复、复验按验收标准在浏览器中实际操作。`"off"` 关闭 |

Paseo 自带的 `/paseo-advisor`、`/paseo-committee` 等编排 skill 也可以单独使用，例如对一个疑难问题请两个模型分别分析；它们不参与流水线（见 ADR 0019）。

## 自动新建工作区（可选）

在项目主目录、主分支上发起的需求，可以用 `--worktree` 启动（`/req` 中的"启动（自动新建工作区）"）：流水线从当前分支切出 `feature/<功能目录名>`，在 Paseo 中新建 worktree 工作区，把需求说明移过去并提交，之后的步骤都在那个工作区中运行，仍然挂在发起的对话下。对话的工作目录不变，查看进度、暂停、继续都在原对话中进行；读写需求文件用通知中给出的完整路径。只能在第一次启动时选择。见 ADR 0018。

## 调度：预约、提醒、自动继续、排队

需要"以后再做"的事，流水线用 Paseo 的定时任务把一条写明步骤的消息发回发起的对话，由对话 agent 执行（机器或 daemon 重启后仍然有效，在 Paseo 的 Schedules 中可以看到）。暂停命令会取消这些预约。

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| （启动参数 `--at`） | — | 预约开始时间：`22:00`、`明天 8:30`、`2026-10-14 08:30`、`+2h` |
| `waitingReminderHours` | 24 | 等待需求方回答、或研发完成后等待测试验证超过这么久，在对话里提醒一次；0 关闭 |
| （启动参数 `--verify-at`） | — | 分阶段时，研发完成后在这个时间自动开始测试验证（写法同 `--at`；隐含分阶段）。研发完成时时间已过就直接继续 |
| `autoResumeMinutes` / `autoResumeMax` | 30 / 2 | 临时错误（重试用完）中断后，这么久之后在对话里自动继续；每次尝试最多几次；0 关闭 |
| `watchdogMinutes` | 0（关闭） | 运行期间对话定时检查，后台进程意外退出时自动继续。每次检查对话 agent 会运行一个回合 |
| `maxConcurrentPipelines` | 0（不限） | 本机同时运行的流水线上限，满了排队。只能写在本机配置中才有意义 |

## 需求总览

`req digest` 在项目目录中列出所有工作区里的需求，按"需要处理、待验收、开发中、对齐中、已验收（最近 7 天）"分组，附用时与用量。`--notify` 同时发给外部通知（事件类型 `digest`）；`--schedule "<cron>"` 让 Paseo 按时间表（本机时区）启动一个短暂的 agent 执行 `req digest --notify`，例如每周一 9 点：`req digest --schedule "0 9 * * 1"`；取消：`req digest --cancel <定时任务 ID>`。

## 团队配置

几台机器、多个项目共用的设置（统一的模型、评审小组、超时、要求的 req-kit 版本）可以放在一份团队配置里。把它放进一个团队共用的 git 仓库，各台机器克隆下来，在本机配置 `~/.req-kit/config.json` 中写上它的路径（绝对路径，或相对 `~/.req-kit/` 的路径）：

```json
{ "teamConfig": "D:/Users/me/team-config/req-kit.json" }
```

合并顺序是 本机 → 团队 → 项目 → spec 中的档位 → 启动参数，后面的覆盖前面的。`daemonUrl`、`daemonPasswordEnv`、`teamConfig` 只在本机配置中生效，写在团队或项目配置里会被忽略并提示。

团队配置中可以写 `"requiredVersion": ">=1.2.0 <2"`。本机的 req-kit 版本不在范围内时，`/req-doctor` 和流水线日志会提醒升级，但不会阻止运行。

## 评审小组（可选）

开启后，标准档的方案审核和代码评审在**第一轮**先由几位评审者（建议使用不同厂商的模型）各自独立评审，再由配置的 `reviewer` 逐条核实、归类（必须修改 / 建议修改 / 留给人决定 / 已驳回），写出正式结论。被驳回和留给人决定的意见记入 `decisions.tsv`，最终报告会展示它们。后续轮次只核对修复，用单个评审者。

```json
"reviewPanel": {
  "enabled": true,
  "steps": ["design_review", "code_review"],
  "profiles": ["standard"],
  "members": [
    { "name": "安全视角", "provider": "codex/<模型 ID>", "modeId": "full-access", "focus": "重点检查权限、输入校验和数据安全" },
    { "name": "可维护性", "provider": "opencode/anthropic/<模型 ID>", "modeId": "build", "featureValues": { "auto_accept": true } }
  ]
}
```

- 成员并行运行，在同一个目录里只读代码、写各自的意见文件（`<功能目录>/review-panel/`），不提交，不改文件。
- 某位成员失败时，只汇总完成的成员；全部失败时该步骤失败。
- 成本：每次启用的评审多出 N 个 agent 的用量，所以默认只用于标准档的第一轮。
- 成员的模型和模式会在 `/req-doctor` 中一并检查。

## 需求总览、决策记录、变更与验收记录

- **需求总览**：`node <req-kit>/bin/start-pipeline.mjs --list` 列出这个仓库所有 worktree 中的需求和各自的阶段（对齐中、开发中、待验收、已验收等）。总览现场生成，不提交到仓库，避免各分支合并时冲突。
- **决策记录** `decisions.tsv`：各步骤把不显而易见的选择（假设、取舍、偏离方案、驳回的评审意见、决定不修的问题）各记一行。会影响结果的标为 `needs_human=yes`，完成报告把它们列入"需要你确认的决定"。
- **变更记录** `changes.md`：每次修改需求（包括方案审核提出问题、验收发现问题）记一节，spec 头部的"版本"随之加 1。
- **验收记录** `acceptance.md`：由 `/req` 的验收手册写，逐条记录验收结果和结论。

格式见 `contracts/feature-files.md`。

## 运行规则

**步骤和轮数**（轮数按档位，在配置的 `profiles` 中调整；下面是标准档的默认值）：

| 环节 | 规则 |
| --- | --- |
| 评审小组（可选） | 开启时，标准档的方案审核和代码评审第一轮先由小组成员并行评审，再由评审者核实汇总 |
| 方案审核 ⇄ 方案修订 | 最多 2 轮审核。判定"阻塞"时暂停并请需求方决定；最后一轮仍要求修改时，修订后直接进入实现 |
| 代码评审 ⇄ 评审问题修复 | 最多 3 轮评审，通过即止；轮数用完时修复后进入下一阶段 |
| 提测说明 | 代码评审之后执行，写 `handoff.md`。分阶段执行时研发阶段到此结束 |
| 服务启动验证 | 方案设计判断项目有常驻服务、且档位开启了 `serviceStart` 时才执行（在已部署的测试环境中验证时不执行） |
| 缺陷修复 ⇄ 复验 | 功能验证发现缺陷时执行，最多 3 轮，复验通过即止（`phases.verify.defects` 为 `handback` 或 `report` 时见上文"执行方式"） |
| 完成报告 | 只要没有暂停或中断就一定执行，遗留问题写进报告 |
| 完成后继续 | 完成后 spec.md 被修改过（需求变更、验收发现问题），`--resume` 从方案设计开始，各步骤在已有方案和代码的基础上只处理变化的部分；没改过则拒绝。`--restart` 则完全从零开始 |
| 增量继续 | 需求变更、回答了方案审核的问题后继续时：方案在原文末尾追加"第 N 次尝试"一节；实现只改需要改的；代码评审只看本次开始以来的改动；验证重新验证变化涉及的验收标准，其余的至少跑一遍现有测试；报告说明是第几次。做法写在 `engine/prompts/incremental.md`，可以用 `prompts.local/` 替换 |

**结果文件**：每步必须写一个 JSON 结果文件，流水线只看它，不看 agent 的回复文字。文件缺失或格式不对时，会在同一个会话里提醒 agent 补写，最多 2 次，仍不对则判定该步骤失败。

**等待与超时**：每步有总时限（`stepTimeoutMinutes`），超时判定失败（agent 可能仍在运行，可在 Paseo 中查看）。等待被拆成每段 10 分钟，连接断开时自动重试。agent 等待权限批准时，同一个请求只通知一次，然后继续等待。

**临时错误自动重试**：步骤因限流（429）、服务暂时不可用（502/503/504/529、overloaded）、网络中断等临时错误失败时，等待后用新的 agent 重做这一步，并告诉它工作区里可能留有上一次没做完的改动。默认最多重试 2 次，分别等 1 分钟和 5 分钟：

```json
"retry": { "attempts": 2, "backoffSeconds": [60, 300] }
```

`attempts` 设为 0 关闭；`backoffSeconds` 的个数少于重试次数时，后面的重试使用最后一个值。超时、结果文件不合格、agent 自己判定失败等不是临时错误，不重试。重试用完仍失败时，中断通知会注明已重试的次数。

**同一个目录一次只运行一条流水线**，因为各步骤都在这个目录中修改和提交。需要并行时，为每个需求使用单独的 worktree 工作区。

## 注意事项

- **发起流水线的聊天 agent 需要能访问本机网络。** 流水线进程继承它的运行环境，需要连接 `ws://127.0.0.1:6767`。用 Codex 做聊天 agent 时，请使用 `full-access` 模式；沙箱模式可能禁止网络。
- **必须在仓库对应的项目对话中发起，对话过程中不要切换工作目录。** 步骤 agent 一律作为子 agent 挂在发起的对话下，而 Paseo 会让子 agent 使用父 agent 的工作目录，所以仓库目录必须就是这个对话的工作目录。在对话中启动时，`--repo` 默认就取对话的工作目录；两者不一致、或发起的对话已不存在时，流水线拒绝启动并说明原因。
- **步骤 agent 以免确认模式运行**，在本机拥有执行命令的权限。提示词禁止了危险操作，但这不是安全边界。请让仓库目录中不包含生产环境凭据。
- **聊天被归档时**，挂在它下面的步骤 agent 也会被归档；通知会发送失败，但流水线会继续运行到结束，结果仍可在 `report.md` 和日志中查看。
- **daemon 重启**会中断正在运行的步骤 agent。流水线会在连续 5 次无法获取状态后判定该步骤失败，之后可以用 `--resume` 继续。
