# 安装与升级

本文面向负责安装的人：通常是开发同事，有经验的测试或产品同事也可以按步骤完成。安装在**运行 Paseo daemon 的那台机器**上做一次，之后这台机器上所有项目的 Paseo 对话都能使用 `/req`。

## 1. 安装布局

程序和本机配置分开存放。升级时只替换程序，配置不动；旧版本目录保留，可以随时回滚。

```text
~/tools/req-kit/versions/
├── 1.0.0/                 一个版本的完整程序（含 node_modules）
└── 1.1.0/                 升级后与旧版本并存
~/.req-kit/
├── config.json            本机配置
├── prompts.local/         本机提示词覆盖（可选）
├── active.json            当前启用的版本
└── install-log/           安装、升级、回滚记录
~/.agents/skills/…          安装器复制的 skill（Codex、Pi、OpenCode 等读取）
~/.claude/skills/…          同上（Claude Code；~/.claude 存在时）
```

Windows 上 `~` 即 `%USERPROFILE%`（如 `D:\Users\<用户名>`）。安装器不使用符号链接，不需要管理员权限。环境变量 `REQ_KIT_HOME` 可以把 `~/.req-kit` 换到别的位置。

## 2. 前置条件

| 项目 | 要求 | 如何确认 |
| --- | --- | --- |
| Paseo | 0.11，daemon 在运行 | Paseo 桌面端能正常对话；默认地址 `ws://127.0.0.1:6767/ws` |
| Node.js | 22 或更新 | `node -v` |
| git | 近期版本 | `git --version` |
| agent | Claude Code、Codex、OpenCode、Pi 至少一种，已在 Paseo 中登录 | 在 Paseo 中用它开一个对话 |
| 网络 | 能访问 GitHub 和 npm 源（或公司镜像） | `npm ping` |
| daemon 密码 | daemon 设了密码时，放在环境变量中（默认 `PASEO_DAEMON_PASSWORD`） | 未设密码可跳过 |

## 3. 首次安装

**第一步：取得程序。** 把要安装的版本放进它自己的版本目录：

```bash
git clone --branch 1.2.0-beta.1 --depth 1 https://github.com/yiyisf/paseo-req-kit ~/tools/req-kit/versions/1.2.0-beta.1
```

Windows PowerShell：

```powershell
git clone --branch 1.2.0-beta.1 --depth 1 https://github.com/yiyisf/paseo-req-kit "$env:USERPROFILE\tools\req-kit\versions\1.2.0-beta.1"
```

**第二步：安装依赖并启用。**

```bash
cd ~/tools/req-kit/versions/1.2.0-beta.1
npm install
node install.mjs
```

`install.mjs` 会：检查 Node.js 和依赖；`~/.req-kit/config.json` 不存在时从示例生成一份；把 `skills/` 下的全部 skill 复制到各 agent 的 skill 目录，并把其中的路径替换为这个版本目录的绝对路径；在每个 skill 目录写入标记文件 `.req-kit-install.json`；记录当前启用的版本。同名目录已存在但不是 req-kit 装的，不会覆盖，除非加 `--force`。

**第三步：填写本机配置。** 编辑 `~/.req-kit/config.json`，为 `builder`（方案设计、实现、修复、报告）和 `reviewer`（方案审核、代码评审、功能验证）各选一个 agent。写法见第 4 节。不确定模型 ID 时运行 `npm run smoke -- check`，它会列出 daemon 上可用的 provider、模型和模式。填好后再运行一次 `node install.mjs`，全部 ✓ 即完成。

团队有统一配置时（统一的模型、评审小组、超时、要求的 req-kit 版本），把团队配置仓库克隆到本机，在本机配置中加上 `"teamConfig": "<团队配置文件的路径>"`（绝对路径，或相对 `~/.req-kit/` 的路径）。团队配置不能设置 daemon 地址和密码。详见 [项目定制与运行规则](项目定制与运行规则.md) 的"团队配置"。

**第四步：体检和冒烟测试。** 先运行：

```bash
node bin/req-doctor.mjs --no-project
```

然后按第 5 节做冒烟测试。

**第五步：接入项目（每个项目一次，推荐）。** 在项目主目录、主分支上开一个 Paseo 对话，输入 `/req-setup`。它会读项目、只问读不出来的事、实际运行验证命令，生成 `.requirement-pipeline/project-notes.md`（项目约定）和 `.requirement-pipeline/verify.md`（验证方法），确认后提交。详见 [项目定制与运行规则](项目定制与运行规则.md)。

**第六步：使用者上手。** 把 [使用者指南](使用者指南.md) 发给使用者，陪他们完成第一个小需求。

### 安装器参数

| 参数 | 作用 |
| --- | --- |
| （无） | 安装或切换到这个版本 |
| `--check` | 只检查，不修改任何文件 |
| `--import-legacy <目录>` | 先从旧脚本版导入配置和 `prompts.local/` |
| `--target <目录>` | 额外安装到另一个 skill 目录（可重复，会被记住，之后的升级也会更新它） |
| `--force` | 覆盖不是 req-kit 安装的同名 skill |
| `--prune` | 列出可以删除的旧版本目录（保留当前和上一个版本） |
| `--uninstall` | 删除 req-kit 安装的 skill，保留 `~/.req-kit` |

## 4. 不同 agent 的配置

每个角色的配置项：

| 字段 | 含义 |
| --- | --- |
| `provider` | `<Paseo 中的 provider ID>/<模型 ID>`，只在第一个 `/` 处拆分 |
| `modeId` | agent 的模式。必须选不会停下来等待批准的模式；没有模式的 agent 不写 |
| `featureValues` | agent 的功能开关，目前只有 OpenCode 需要 |
| `thinkingOptionId` | 可选，思考强度，可用值取决于 agent 和模型 |

| agent | `provider` 写法 | 无人值守的设置 | 思考强度 |
| --- | --- | --- | --- |
| Claude Code | `claude/<模型 ID>` | `"modeId": "bypassPermissions"` | 取决于模型 |
| Codex | `codex/<模型 ID>` | `"modeId": "full-access"` | 取决于模型 |
| OpenCode | `opencode/<上游>/<模型 ID>` | `"modeId": "build"` 加 `"featureValues": { "auto_accept": true }` | 取决于模型（variant） |
| Pi | `pi/<上游>/<模型 ID>` | 不写 `modeId`（Pi 没有模式，也不请求批准） | `off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max` |

以上来自 Paseo 0.11.2 源码，以你的 daemon 实际返回为准（`npm run smoke -- check` 或 `/req-doctor`）。

- **Claude Code**：其他模式（`default`、`acceptEdits`、`auto`）都可能停下来等待批准，`plan` 不能改文件，都不适合流水线。
- **OpenCode**：模型 ID 带上游前缀，如 `anthropic/...`、`openai/...`。模式就是 OpenCode 中定义的 primary agent，默认 `build` 可以改文件和执行命令。不开 `auto_accept` 的话，执行命令时会停下来等待批准。
- **Pi**：写了 `modeId` 会被 daemon 拒绝。只有装了会弹出确认的 Pi 扩展时，才可能停下来等待。

混用示例：

```json
"agents": {
  "builder":  { "provider": "claude/<模型 ID>", "modeId": "bypassPermissions" },
  "reviewer": { "provider": "opencode/openai/<模型 ID>", "modeId": "build", "featureValues": { "auto_accept": true } }
}
```

### 作为聊天 agent（使用者对话的那一个）

| agent | 读取 skill 的位置 | 如何触发 |
| --- | --- | --- |
| Claude Code | `~/.claude/skills` | `/req 我想……` |
| OpenCode | `~/.agents/skills`（也读 `~/.claude/skills`） | `/req 我想……`；命令列表中没有时直接说"用 req 帮我……" |
| Pi | `~/.agents/skills` | `/skill:req 我想……` |
| Codex | `~/.agents/skills` | 直接说"用 req 帮我……"，或用 Codex 点名 skill 的方式 |

聊天 agent 需要能执行命令和访问本机网络（流水线要连接 daemon）。用 Codex 做聊天 agent 时请用 `full-access` 模式。新开的对话立即可用，已经打开的对话需要新开一个。

## 5. 冒烟测试

编排逻辑已在模拟环境中测试过，下面四项确认的是你的真实环境。第一次安装、更换 agent、升级 Paseo 后都建议做一遍。命令在当前版本目录中运行。

| # | 测什么 | 怎么测 | 预期 |
| --- | --- | --- | --- |
| 1 | daemon、模型和模式 | 终端运行 `npm run smoke -- check` | 两个角色各启动一个小 agent，能写文件、能执行命令、不停下等权限 |
| 2 | 通知回发、子 agent 挂载 | 在 Paseo 对话中让聊天 agent 执行 `npm run smoke -- notify`（先 `cd` 到版本目录） | 对话中出现"通知通道工作正常"；子 agent 列表出现"[冒烟测试] 子 agent" |
| 3 | 回合结束后后台进程是否存活 | 让聊天 agent 执行 `npm run smoke -- detach-start` 并结束本轮；一分钟后再让它执行 `npm run smoke -- detach-check` | 显示 ✓。显示 ✗ 说明环境会终止后台进程，需要改用插件方式启动 |
| 4 | 完整跑一遍 | 在一个测试项目的 worktree 对话中输入 `/req 在 README 末尾加一行版权声明` | 走快速档，收到进展和完成通知；功能目录中各产物齐全；工作分支上有本地提交 |

第 2、3 项依赖对话提供的 `PASEO_AGENT_ID`、`PASEO_AGENT_CWD`，必须在 Paseo 对话中由聊天 agent 执行。

## 6. 升级

以从 1.0.0 升到 1.1.0 为例。

1. 阅读 `CHANGELOG.md` 中两个版本之间的"升级须知"。
2. 运行 `node bin/req-doctor.mjs --no-project`，确认当前状态正常。正在运行的流水线不用停，见下表。
3. 把新版本放进新的版本目录，安装依赖并启用：

```bash
git clone --branch 1.1.0 --depth 1 https://github.com/yiyisf/paseo-req-kit ~/tools/req-kit/versions/1.1.0
cd ~/tools/req-kit/versions/1.1.0
npm install
node install.mjs
```

PowerShell：

```powershell
git clone --branch 1.1.0 --depth 1 https://github.com/yiyisf/paseo-req-kit "$env:USERPROFILE\tools\req-kit\versions\1.1.0"
cd "$env:USERPROFILE\tools\req-kit\versions\1.1.0"
npm install
node install.mjs
```

4. 至少跑冒烟测试第 1 项；升级须知提到通知、后台进程或启动方式有变化时，再跑第 2、3 项；主版本升级跑全部四项。
5. 把"使用者会看到的变化"转给使用者，提醒新需求请开新对话。

安装器替换各 agent 目录中带标记的 skill，把路径指向新版本，删除新版本不再包含的旧 skill，并更新启用记录。不会动：`~/.req-kit/` 下的配置和提示词覆盖、各项目仓库中的文件、不是 req-kit 安装的 skill。

| 升级时的状态 | 会发生什么 |
| --- | --- |
| 还在聊天对齐阶段 | 对话已加载的是旧版 skill，继续使用即可；启动的是新版引擎 |
| 流水线正在运行 | 进程已载入旧版代码，旧版本目录仍在，按旧版跑完 |
| 已暂停、失败或等待需求方决定 | 继续时由新版引擎读取；状态格式有变化时自动迁移，原文件备份为 `state.json.bak-v<旧版本>` |
| 已完成 | 不受影响 |

## 7. 回滚

在旧版本目录中重新运行安装器即可：

```bash
cd ~/tools/req-kit/versions/1.0.0
node install.mjs
```

这会把 skill 和引擎路径改回 1.0.0，配置不变。如果某个功能目录的状态文件已被新版迁移，旧版引擎会拒绝继续并提示：把 `state.json.bak-v<旧版本>` 恢复为 `state.json`，或者用 `--restart` 从头开始。

旧版本目录建议保留到新版本稳定运行一周以上、且没有由它启动的流水线仍在运行。`node install.mjs --prune` 会列出可以删除的旧版本。

## 8. 从脚本版（paseo-requirement-workflow）迁移

适用于已经装了 `~/tools/requirement-pipeline` 和 `/requirement-kickoff` 的机器。

| 对象 | 脚本版 | req-kit | 迁移方式 |
| --- | --- | --- | --- |
| 入口 | `/requirement-kickoff` | `/req` | 安装器替换旧的 skill；1.x 期间保留同名的引导入口，提示改用 `/req` 并转交 |
| 本机配置 | `~/tools/requirement-pipeline/pipeline.config.json` | `~/.req-kit/config.json` | `node install.mjs --import-legacy ~/tools/requirement-pipeline`，同时导入 `prompts.local/`；顶层 `rounds` 继续有效 |
| 项目配置 | `.requirement-pipeline.json`、`.requirement-pipeline/` | 同名同位置 | 无需迁移 |
| 功能目录 | `docs/features/<日期>-<名称>/` | 同左 | 无需迁移；没有 `version` 字段的状态文件按第 1 版读取 |
| 术语文件 | `CONTEXT.md` | `GLOSSARY.md` | 继续读取 `CONTEXT.md`，新术语写入 `GLOSSARY.md` |
| 依赖的外部 skill | `grilling`、`domain-modeling` | 不再需要 | 可以保留，也可以自行卸载 |

建议顺序：

1. 等脚本版启动的流水线跑完（或记下它们，迁移后用新版续跑）。
2. 按第 3 节取得程序并 `npm install`，然后运行 `node install.mjs --import-legacy ~/tools/requirement-pipeline`。
3. 跑冒烟测试第 1–3 项。
4. 告诉使用者入口改为 `/req`。
5. 一周后删除 `~/tools/requirement-pipeline`。

## 9. Paseo 或 agent 升级之后

运行 `/req-doctor`（或 `node bin/req-doctor.mjs`），确认 SDK 版本在支持范围内、配置中的模型和模式仍然存在；然后跑冒烟测试第 1–3 项。有失败时，先看 req-kit 是否已有适配的新版本；没有的话，把输出反馈给维护者，并暂时回退 Paseo 或 agent 的版本。

## 10. 卸载

```bash
node ~/tools/req-kit/versions/<当前版本>/install.mjs --uninstall
```

这会删除 req-kit 安装的 skill。确认不再使用后，再手工删除 `~/tools/req-kit` 和 `~/.req-kit`。各项目中的配置文件和功能目录保留，它们本身就是文档。

## 11. 安全提示

- 步骤 agent 以免确认模式运行，可以在本机执行命令。仓库和本机环境变量中不要放生产凭据；最好用专门的开发机或虚拟机运行 daemon。
- 流水线只做本地提交，合并和上线始终由人决定。
