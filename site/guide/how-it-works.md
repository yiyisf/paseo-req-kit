# 工作原理

req-kit 由三部分紧密协同组成：
1. **对话中的 Skill**：`/req` 访谈入口、各阶段方法指令；
2. **后台流水线引擎**：驱动方案设计、实现、评审、验证、报告等 9 个子步骤；
3. **原则与规范文件约定**：连接各 Agent 的标准输入与输出契约。

---

## 全景流水线架构

流水线采用**“做检分离”**机制：每个步骤是一个**全新的** Paseo Agent，作为子 Agent 挂载在发起的对话下（如 `[20261012-sms-login] 6-代码评审 第2轮`）。步骤之间不依赖大模型的易失上下文记忆，完全通过功能目录里的文件交接：

## 三条核心运行铁律

::: tip 1. 结论只看规范结果文件
每个步骤结束前，必须在功能目录输出格式严格的 JSON 结果文件（例如 `{"verdict": "changes_required"}`）。流水线引擎仅据此判定下一步走势，**绝不通过文本大模型模糊解析 Agent 的回复文字**。如果文件缺失或格式不符，会在该会话内强制打回补写。
:::

::: tip 2. 做事的和检查的必须分离
- **Builder (实现者)**：负责架构设计、编写功能代码、修复缺陷；
- **Reviewer (检查者)**：负责方案合规审核、代码安全评审、功能验收验证；
- 建议为两个角色配置不同的大模型提供商（例如 Claude 3.5 Sonnet + GPT-4o 交叉审阅）。**验证步骤只登记缺陷证据、绝不私自改动产品代码**。
:::

::: tip 3. 从严判定，讲求铁证
交付报告从严判定："已完成，可以验收"的前提是需求说明（`spec.md`）中的**所有验收标准均包含可复现的执行证据（截图、网络日志、终端输出）**；未验证的项必须直接标明为"未验证"，绝不隐瞒遗留缺陷。
:::

## 规范功能目录结构

每一个需求的所有生命周期产物统一收敛在 `docs/features/<日期>-<英文短名>/` 中，并作为常规代码提交留存在仓库中：

```text
docs/features/20261012-sms-login/
├── spec.md              需求说明（经你确认的标准版本）
├── alignment.md         访谈记录与初始诉求
├── design.md            技术方案设计与模块划分
├── design-review.md     方案审核记录与修改建议
├── implementation.md    代码实现细节与 TDD 测试记录
├── code-review.md       代码交叉评审意见与整改记录
├── handoff.md           提测说明（改动范围、启动方法、注意事项）
├── verification.md      功能验证过程与验收证据链
├── report.md            结单交付报告（总结与遗留问题）
├── decisions.tsv        过程中所做的架构与业务决定
└── results/             各步骤机器可读的结果文件
```

## 流程中断与状态机恢复

流水线引擎的状态完整持久化在 `.pipeline/state.json` 中：
- **意外中断安全**：机器重启、网络中断或超时，执行命令即可从上一个成功节点精准恢复；
- **局部返工自适应**：若需求细节在评审阶段微调，系统仅触发受影响步骤增量重跑，无需推倒重来。

👉 了解多角色提测与分阶段控制，请参阅 **[分阶段执行与提测](./phases)**。
