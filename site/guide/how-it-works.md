# 工作原理

req-kit 由三部分组成：对话中的 **skill**（`/req` 等入口和方法）、后台的**流水线引擎**（驱动第 3–11 步），以及两者共用的**原则和文件约定**。

```text
Paseo 对话（/req）                                   流水线引擎（后台进程）
  访谈 → spec.md → 独立审阅 → 用户确认
  执行启动命令 ─────────────────────────────────►  检查条件，后台启动，立即返回
                                                    研发：方案设计 → 方案审核 ⇄ 修订 → 实现
                                                         → 代码评审 ⇄ 修复 → 提测说明
                                                    ┄┄ 闸口（分阶段时停在这里，等待提测）┄┄
                                                    验证：服务启动 → 功能验证 → 缺陷修复 ⇄ 复验
                                                    → 完成报告
  ◄── 需要业务决定：问题 + 继续命令 ───────────────  （暂停，还没写代码）
  ◄── 进展 / 等待批准 / 中断原因 ──────────────────
  ◄── 结论 + 摘要 + report.md ────────────────────
```

## 步骤

每个步骤是一个**新的** Paseo agent，作为子 agent 挂在发起的对话下，名字形如 `[20261012-sms-login] 6-代码评审 第2轮`。步骤之间不靠对话记忆，只靠功能目录里的文件交接。

| 步骤 | 执行者 | 产物 | 什么时候执行 |
| --- | --- | --- | --- |
| 方案设计 | builder | `design.md` | 总是；开启方案提案时先由几个 agent 各提一份 |
| 方案审核 ⇄ 修订 | reviewer ⇄ builder | `design-review.md` | 标准档最多 2 轮；发现只有需求方能回答的问题时暂停并发回对话 |
| 代码实现 | builder | 代码、`implementation.md` | 适合时用 TDD |
| 代码评审 ⇄ 修复 | reviewer ⇄ builder | `code-review.md` | 标准档最多 3 轮；开启评审小组时第一轮并行评审 |
| 提测说明 | builder | `handoff.md` | 总是；研发阶段的最后一步 |
| 服务启动 | builder | `service-start.md` | 项目有常驻服务、档位开启时 |
| 功能验证 | reviewer | `verification.md` | 总是（只做研发时除外）；按验收标准逐条给出证据 |
| 缺陷修复 ⇄ 复验 | builder ⇄ reviewer | `verification.md` | 发现缺陷时，最多 3 轮 |
| 完成报告 | builder | `report.md` | 只要没有暂停或中断就执行 |

builder 和 reviewer 是两个角色，在配置中各选一个 agent，建议用不同的模型。

## 三条基本规则

**结论只看结果文件。** 每一步最后写一个 JSON 结果文件（例如 `{"verdict": "changes_required"}`），流水线据此决定下一步，不解析 agent 的回复文字。缺失或格式不对时，在同一个会话里提醒补写。

**做事的和检查的分开。** 审核、评审、验证由 reviewer 完成；验证步骤只登记缺陷、不改产品代码。

**如实。** 报告从严判定："已完成，可以验收"要求所有验收标准都有通过的证据；没验证的就写"未验证"。

## 功能目录

一个需求的所有产物都在 `docs/features/<日期>-<英文短名>/` 中，随代码一起提交：

```text
docs/features/20261012-sms-login/
├── spec.md              需求说明（你确认的版本）
├── alignment.md         访谈记录
├── design.md            方案
├── design-review.md     方案审核
├── implementation.md    实现记录
├── code-review.md       代码评审与处理记录
├── handoff.md           提测说明
├── verification.md      功能验证与复验
├── report.md            完成报告
├── decisions.tsv        过程中的决定（需要你确认的会列进报告）
├── progress.md          每一步的时间线
└── .pipeline/           运行状态、结果文件、日志（不提交）
```

## 出了问题怎么办

- **临时错误**（限流、网络中断）：自动等待重试；仍然失败时中断，并预约半小时后在对话里自动继续。
- **需要你决定**：方案审核发现只有需求方能回答的问题，流水线在写代码之前暂停，问题发回对话。回答并更新需求说明后继续，从方案设计开始增量处理。
- **你改了需求**：继续时从方案设计开始，在已有方案和代码的基础上只处理变化的部分。
- **进程意外退出**：执行继续命令即可，已完成的步骤沿用结果。
