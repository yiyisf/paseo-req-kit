# 工作原理

req-kit 由三部分紧密协同组成：
1. **对话中的 Skill**：`/req` 访谈入口、各阶段方法指令；
2. **后台流水线引擎**：驱动方案设计、实现、评审、验证、报告等子步骤；
3. **原则与规范文件约定**：连接各 Agent 的标准输入与输出契约。

---

## 全景流水线架构

流水线采用**“做检分离”**机制：每个步骤是一个**全新的** Paseo Agent，作为子 Agent 挂载在发起的对话下（如 `[20261012-sms-login] 6-代码评审 第2轮`）。步骤之间不依赖大模型的易失上下文记忆，完全通过功能目录里的文件交接：

### 步骤与执行角色速览

| 步骤 | 执行者 | 核心产物 | 什么时候执行 |
| :--- | :--- | :--- | :--- |
| **方案设计** | Builder | `design.md` | 总是；开启方案提案时先由几个 agent 各提一份 |
| **方案审核 ⇄ 修订** | Reviewer ⇄ Builder | `design-review.md` | 标准档最多 2 轮；发现只有需求方能回答的问题时暂停并发回对话 |
| **方案确认** | 你 (使用者) | `preview.md`、`prototype/` | 标准档的界面改动：写代码之前请你确认"做完后会看到什么" |
| **代码实现** | Builder | 代码、`implementation.md` | 适合时用 TDD；标准档方案若拆分了切片（slices）则逐片实现，每片启动一个新 agent |
| **代码评审 ⇄ 修复** | Reviewer ⇄ Builder | `code-review.md` | 标准档最多 3 轮；第一轮由规格评审和规范评审双轴并行，再汇总（开启评审小组时由小组成员并行） |
| **提测说明** | Builder | `handoff.md` | 总是；研发阶段的最后一步，交付关键信息 |
| **服务启动** | Builder | `service-start.md` | 项目有常驻服务、档位开启时 |
| **功能验证** | Reviewer | `verification.md` | 总是（只做研发时除外）；按验收标准逐条给出证据 |
| **缺陷修复 ⇄ 复验** | Builder ⇄ Reviewer | `verification.md` | 发现缺陷时，最多 3 轮 |
| **完成报告** | Builder | `report.md` | 只要没有暂停或中断就执行，全面总结 |

## 按需求类型走不同的做法

需求说明（`spec.md`）头部的“类型”一行决定了流水线的侧重。步骤依然规范统一，但针对不同类型会有更匹配的工程做法：

| 需求类型 | 针对性工程做法 |
| :--- | :--- |
| **新需求、小改动** | 遵循标准流水线全套流程 |
| **缺陷 (Bugfix)** | 方案设计转为**复现与定位**：先提交一个修复前必然失败的复现测试，确证根因再修复；无法复现则停下，将需要补充的信息发回对话 |
| **重构 (Refactor)** | 先用特征测试（Characterization Test）**锁住现有系统行为**，再小步迭代改动、保证每步测试全绿；评审首要审查系统行为是否发生漂移 |
| **评估 (Assessment)** | **只读调研**：调研评估 → 评估审阅 ⇄ 修订 → 评估报告，不写业务代码；报告附需求草稿，可直接一键转为后续新需求 |

## 三条核心运行铁律

::: tip 1. 结论只看规范结果文件
每个步骤结束前，必须在功能目录输出格式严格的 JSON 结果文件（例如 `{"verdict": "changes_required"}`）。流水线引擎仅据此判定下一步走势，**绝不通过文本大模型模糊解析 Agent 的回复文字**。如果文件缺失或格式不符，会在该会话内强制打回补写。
:::

::: tip 2. 做事的和检查的必须分离
- **Builder (实现者)**：负责架构设计、编写功能代码、修复缺陷；
- **Reviewer (检查者)**：负责方案合规审核、代码安全评审、功能验收验证；
- 建议为两个角色配置不同的大模型提供商（例如 Claude 3.5 Sonnet + GPT-4o 交叉审阅）。**验证步骤只登记缺陷证据、绝不私自改动产品代码**。
:::

::: tip 3. 从严判定，讲求铁证
交付报告从严判定："已完成，可以验收"的前提是需求说明（`spec.md`）中的**所有验收标准均包含可复现的执行证据（截图、网络日志、终端输出）**；未验证的项必须直接标明为"未验证"，绝不隐瞒遗留缺陷。
:::

## 规范功能目录结构

每一个需求的所有生命周期产物统一收敛在 `docs/features/<日期>-<英文短名>/` 中，并作为常规代码提交留存在仓库中：

```text
docs/features/20261012-sms-login/
├── spec.md              需求说明（经你确认的标准版本）
├── alignment.md         访谈记录与初始诉求
├── design.md            技术方案设计（缺陷为 diagnosis.md，评估写 assessment.md）
├── design-review.md     方案审核记录与修改建议
├── preview.md           界面预览说明与效果图（界面改动时）
├── implementation.md    代码实现细节与 TDD 测试记录
├── code-review.md       代码交叉评审意见与整改记录
├── handoff.md           提测说明（改动范围、启动方法、注意事项）
├── verification.md      功能验证过程与验收证据链
├── report.md            结单交付报告（总结与遗留问题）
├── decisions.tsv        过程中所做的架构与业务决定
├── progress.md          每一步执行的时间线沉淀
└── .pipeline/           运行状态、机器结果文件、日志（不随代码提交）
```

## 异常中断与状态机恢复

流水线引擎的状态完整持久化在 `.pipeline/state.json` 中，具备高度容错与自愈能力：

- **临时错误**（模型限流、网络中断）：自动等待指数退避重试；重试耗尽时平稳中断，并在对话中预约半小时后自动唤醒继续；
- **需要业务决定**：方案审核发现只有需求方能决定的问题，或缺陷无法复现时，流水线在写代码前主动暂停并向你发问。回答并更新需求说明后即可增量继续；
- **需求发生调整**：在已有方案和代码的基础上增量比对，只处理变化的部分，绝不盲目全量推翻；
- **进程意外退出**：重新输入继续命令即可，已跑通的步骤直接复用结果，秒级续跑。

👉 了解多角色提测与分阶段控制，请参阅 **[分阶段执行与提测](./phases)**。
