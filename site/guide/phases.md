# 分阶段执行与提测

在实际团队协作中，研发和测试通常由不同同事负责，具备不同的节奏与环境诉求：研发完成需要“提测”，测试同事需要先行拉起或部署测试环境、导入测试数据，再进行回归测试。

req-kit 将流水线明确划分为**研发阶段**与**测试验证阶段**，中间设立严格的**阶段闸口**。

## 规范提测说明（`handoff.md`）

研发阶段的收官产物是标准提测说明文档 `handoff.md`，无论是何种执行模式都会严格产出，包含 6 大核心板块：

1. **改动功能清单**：按功能点归纳修改内容，附带对应 Git 分支与 Commit 列表；
2. **环境启动指南**：依赖包变更、数据库变更迁移（Migration）、新增配置项及启动指令；
3. **自测充分性证据**：单元测试覆盖情况、代码评审通过结论、自动化测试结果；
4. **测试侧重建议**：系统高危边界场景、可能受波及的回归范围；
5. **已知遗留问题**：明确未完成项与边缘限制；
6. **测试前置准备**：测试环境账号配置、数据初始化要求（**只提供获取凭据的安全指引，绝不明文写入真实密码**）。

## 如何启动测试验证

当分阶段流水线停在闸口并通知“研发完成，可以提测”后，你在对话中输入：

```text
开始测试验证
```

AI 会简要向你复述一遍提测说明，并同你确认两个核心决策：
- **验证所在环境**：选择“本地自动启动服务”还是对“已部署的独立测试环境”进行验证；
- **发现缺陷的策略**：支持现场修复并复验、退回研发阶段重新提测，或仅记录缺陷后结单。

::: info 支持定时预约验证
如果你希望在下班后或非高峰期启动验证，可以在发起时追加时间参数：
`start-pipeline --verify-at 22:00`，流水线将在研发完毕后自动于 22:00 唤醒并执行测试。
:::

## 测试同事多工作区分工接手

对于配置了“开发时自动新建工作区”的需求，研发完成后，测试同事可在该项目**任何工作区**的 Paseo 对话中直接运行指令接手：

```text
/req 开始测试验证 sms-login
```

测试验证期间的所有通知与对话将定向路由给测试同事，而底层执行仍然隔离在需求对应的独立工作区中，互不干扰。

## 核心配置项速查

| 配置键名 | 默认值 | 可选值 | 配置作用与影响 |
| :--- | :--- | :--- | :--- |
| `phases.mode` | `"continuous"` | `continuous` / `gated` / `develop-only` | 全局默认执行模式 |
| `phases.verify.environment` | `"local"` | `local` / `deployed` | 测试阶段目标环境：本地运行 或 外部已部署测试机 |
| `phases.verify.agents` | `{}` | JSON Object | 测试阶段指定专属 Agent（如配置测试专用 Profile） |
| `phases.verify.defects` | `"fix"` | `fix` / `handback` / `report` | 发现缺陷时的处理行为：原地修复 / 退回研发 / 仅上报 |
| `phases.verify.serviceStart` | `null` | `true` / `false` / `null` | 是否在测试前启动常驻服务；为 null 时跟随需求档位 |

更多技术架构决策详情，请参阅 [ADR 0022：分阶段执行与提测设计决定](/reference/adr/0022-develop-and-verify-phases)。
