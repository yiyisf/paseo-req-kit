每个版本分为"使用者会看到的变化"和"升级须知"。升级步骤见 docs/guide/安装与升级.md。

1.12.0 ​

稳定版：少等人，内容同 1.12.0-beta.1 至 beta.4（详见下面各条），设计决定见 ADR 0031。

使用者会看到的变化 ​

  • 自愈：超时时 agent 还在做就多等一轮；agent 报错、结果文件无效时新开 agent 重做一次；限流时按 Paseo 的额度恢复时间预约自动继续；可选的备用模型（agents.fallback）。
  • 方案审核的问题先自答，只把业务取舍连同推荐答案交给需求方。
  • 后台进程意外退出后自动继续：定时检查默认每 60 分钟；接单器也会发现并续跑。
  • 装好就选好模型：安装时自动选 builder、reviewer 和备用模型；插件设置中有"模型"页。
  • /req 少问：工作区、档位、执行方式、开始时间按推荐值走，确认摘要写明；卡片回复写"好的"也算同意。
  • 插件："等你处理"收件箱（直接确认方案、回答问题、继续），"配置"页列出全部设置和来源。
  • 接单器：自检与告警、草稿合并请求（push.mergeRequest）、小改动自动确认（autoConfirm.hours）、按人通知（people）。
  • req stats："人工介入"一节：停下等人的原因、自动处理的次数和比例。

升级须知 ​

  • 默认行为的变化：selfHeal、answerQuestionsFirst 默认打开，watchdogMinutes 默认从 0 改为 60。想保持 1.11 的行为，分别设为 false、false、0。
  • 新配置都可选：agents.fallback、push.mergeRequest、autoConfirm、people。
  • 外部通知新增事件 alert 和字段 people；状态文件和使用记录新增 stopKind、recoveries，旧文件照常可用。
  • 从 1.11 升级后运行 paseo plugin reload req-kit（或重启 Paseo）加载新插件。

1.12.0-beta.4 ​

  • 修正：1.12.0-beta.3 的 Paseo 插件加载失败（"Invalid plugin RPC method: req.setAgents"）。Paseo 要求插件接口名只用小写字母、数字和 . _ -，改为 req.set-agents；测试中加上了这条规则的检查。其余内容同 1.12.0-beta.3。

1.12.0-beta.3 ​

接单机器能自己发现问题；插件里可以直接处理等你的事、看到全部配置。

使用者会看到的变化 ​

  • 插件"等你处理"：需求首页最上面列出所有等人处理的事（确认方案、回答问题、中断、未完成），等得最久的在前，写明要做什么、等了多久。方案可以直接确认或写修改意见，问题可以直接回答，插件把回复转给需求的对话，和在对话里回答一样（req reply）。
  • 插件"配置"页：首页的"配置"按主题列出 req-kit 的全部设置，每项写明是什么、现在的值、来自本机、团队还是项目的配置文件；可以按项目查看、搜索、只看改过的。只看不改，页尾写明各项怎么改。密钥和个人账号不显示。
  • 接单器自检与告警：每次检查前确认 Paseo 在线、agent 已登录、额度没用完、需求管理系统的命令可用；不正常时暂停接单，并通过外部通知告警一次（新事件 alert），恢复时再说一次。
  • 草稿合并请求（可选，push.mergeRequest）：推送分支后用机器上已登录的 glab 等命令建草稿合并请求，描述是提测说明和卡片链接，地址写进卡片。合并仍由人做。req doctor 检查是否已登录。
  • 小改动自动确认（可选，autoConfirm.hours，默认关闭）：快速档、没有待答问题的卡片，AI 区写明到时没有异议就开始。
  • 按人通知：通知事件带上发给谁（people）：需求方要处理的事和结果发给卡片的提出人，账号来自配置的 people；其余发到群。内部 IM 适配器拿到接口后可以直接用。

升级须知 ​

  • 新配置 push.mergeRequest、autoConfirm、people（都只在需要时写）。people、push 只能写在本机或团队配置中。
  • 外部通知新增事件类型 alert 和字段 people；只订阅了部分事件的通知模块不受影响。
  • 新命令 req reply、req api config；req api list 的每一项多了 waiting。

1.12.0-beta.2 ​

1.12.0-beta.1 的内容（见下），加一处修正：

  • 修正：安装时自动选模型，Paseo 没有运行时会一直等待连接；现在 20 秒连不上就放弃，改为提示之后运行 req configure --auto。1.12.0-beta.1 因此没有发布。

1.12.0-beta.1 ​

少等人：能自动处理的中断不再停下等人，选择题改为默认值，装好就选好模型。设计决定见 ADR 0031。

使用者会看到的变化 ​

  • 自愈：步骤超时而 agent 还在做时，再等它一轮；agent 报错、没写出有效结果时，新开一个 agent 重做一次。限流重试用完时，预约在 Paseo 显示的额度恢复时间之后自动继续，而不是固定 30 分钟。
  • 备用模型（可选）：配置 agents.fallback 后，报错重做、限流重试用完时换它把这一步做完。req configure 和插件的"模型"设置页会推荐一个。
  • 方案审核的问题先自答：审核说需要需求方决定时，先由 builder 从代码和文档中找答案，只把真正的业务取舍连同推荐答案交给需求方；都能回答时不停下。
  • 后台进程意外退出后自动继续：定时检查默认打开（每 60 分钟）；接单器每次检查时也会发现并请对话继续。
  • 装好就选好模型：安装时自动选好已登录的 agent（两个不同厂商分别做 builder 和 reviewer，再选一个做备用），不再需要回答配置向导；req configure --auto 同样。插件设置中新增"模型"一页，可以直接修改。
  • /req 少问：不再问是否新建工作区、档位、执行方式、现在开始还是预约，按推荐值直接走，确认摘要最后一行写明，想改再说；确认需求说明后立即开始。
  • 卡片回复更宽松：写"好的""没问题""按你说的来"也算同意；回复区只写了一句"好的"也算确认。卡片已经写清需求时，不再为提问而提问；问题附上推荐答案。
  • req stats 新增"人工介入"一节：停下等人的原因、自动处理的次数、到达提测的需求中没有非必要介入的比例。

升级须知 ​

  • 新配置 selfHeal、answerQuestionsFirst（默认都是 true）、agents.fallback（可选）；watchdogMinutes 默认从 0 改为 60。想保持以前的行为，分别设为 false、false、0。
  • 状态文件新增 stopKind、recoveries，使用记录的 run 新增 stopKind、recoveries；旧文件照常可用，统计按状态推断旧记录的原因。

1.11.0 ​

稳定版：包含 1.10 的"从卡片开始的需求"和 1.11 的接单器（详见下面的 beta 记录），并修正步骤超时后会重复开 agent 的问题。

使用者会看到的变化 ​

  • 从卡片开始的需求（1.10）：req start --from <系统>:<卡号> 读卡片、建需求会话；卡片描述末尾的 AI 区和需求方回复区代替对话；按子系统自动选仓库；工厂模式下研发完成后可以推送 req/ 分支；统计按需求方汇总。
  • 接单器（1.11）：req factory 定时接标题带 [AI]/【AI】 的新卡片，并把需求方的回复转给需求会话。
  • 修正：步骤超时后不再重复开 agent。以前超时只判定失败、不看 agent 实际状态，继续时会新建一个 agent，而旧的仍在运行，两个 agent 同时改同一批文件、在同一个工作区提交、写同一个结果文件，需要手动停止旧的。现在继续（--resume、自动重试）时先看上一次的 agent：做完了就用它的结果；还在做就接着等它一轮；第二次仍超时才停止它，再新建。连续读不到 agent 状态时同样处理。

升级须知 ​

  • 从 1.9 升级：先看 1.10.0-beta.1 至 1.11.0-beta.1 的升级须知（对接配置的 query、describe、list，项目配置的 cardSource，本机或团队配置的 push、factory）。不用卡片的项目不需要改任何配置。
  • 状态文件的步骤记录新增 leftRunning、reattached 两项，旧状态文件照常可用。

1.11.0-beta.1 ​

接单器：一台共享研发机器自动接卡片、转达回复，需求方只在卡片上操作。

使用者会看到的变化 ​

  • req factory：每隔几分钟（factory.pollMinutes，默认 5）检查一次需求管理系统：本机登记的仓库所在空间中，标题以 [AI] 或 【AI】 开头、还没开始过的卡片，自动按子系统进入对应仓库、开始需求；需求方在卡片中的新回复自动转给需求会话。
    • req factory once 检查一次；start / stop 在后台运行；status 看最近一次检查和没能接的卡片；service 给出作为系统服务（开机自动运行）的写法。
    • 每次最多开始 3 个需求（factory.maxNewPerPoll），其余下次再接；接不了的卡片记下原因，卡片改了马上再试，否则一天后再试。
  • 修正：req start --from 在建需求会话时失败（例如 Paseo 没在运行）后，再运行一次会补建会话，而不是提示"已经开始过"。

升级须知 ​

  • 需要在对接配置中加上 list（列出卡片的命令），写法见《项目定制与运行规则》的"接单器"一节；接单的仓库要在 cardSource 中写上空间（projectId）。
  • 新增配置 factory（只能写在本机或团队配置中）、本机目录 ~/.req-kit/factory/。现在只支持一台机器接单。设计决定见 ADR 0030。

1.10.0-beta.3 ​

从卡片开始的需求：按子系统自动选仓库、研发完成后推送分支、统计按需求方汇总。

使用者会看到的变化 ​

  • 按子系统选仓库：在仓库中运行 /req-setup 时可以写上这个仓库接哪个空间、哪些子系统的卡片（同一子系统有几个仓库时再写标题关键字），并在本机登记。之后 req start --from ALM:<卡号> 不用写 --repo。req card route 查看本机登记的仓库。
  • 推送分支（默认关闭）：本机或团队配置打开 push 后，从卡片开始的需求在研发完成、写好提测说明后推送到 origin 的 req/<卡号简称> 分支，分支名写进卡片。不强推、不合并。
  • 统计：运行记录带上需求方和卡号，req stats --report 多一节"从卡片开始的需求（按需求方）"，CSV 多 requester、card 两列。

升级须知 ​

  • 都是可选的。推送只在 push.enabled 为 true、需求是从卡片开始的时候发生，并且只能在本机或团队配置中打开（ADR 0029 记录了这条对"只在本地提交"规则的放宽）。
  • 新增项目配置 cardSource、本机文件 ~/.req-kit/card-repos.json、状态文件可选字段 pushed、运行记录可选字段 requirement.requester 和 requirement.source，格式版本都不变。

1.10.0-beta.2 ​

（1.10.0-beta.1 的发布任务因一个测试的顺序问题失败，没有发布，内容相同，以 beta.2 发布。）

从卡片开始需求：需求方在需求管理系统中写好卡片，不必有人在 Paseo 对话里发起；问题和确认通过卡片描述往来。这是"软件工厂"的第一步，定时接单器在 1.11。

使用者会看到的变化 ​

  • req start --from <系统>:<卡号>：读一张卡片，建功能目录，在 Paseo 中为这个需求建一个需求会话。需求会话按新的无人值守手册从卡片写需求说明，把摘要、验收标准、假设和问题写进卡片描述末尾的"req-kit AI 区"；需求方在"需求方回复"区回答，写"确认：同意"后它自己启动开发（自动新建工作区）。需求方自己写的描述原样保留。
  • req card check [<卡号> | --all]：读需求方的回复，把新的回答、补充、描述修改和确认转给需求会话；同样的内容只转一次。req card list 列出本机从卡片开始的需求。
  • 开发中卡片跟着走：状态按 statusMap 改（例如"开发中""待测试"），AI 区更新进度；方案待确认时附上方案摘要，需求方在"方案确认："后写"同意"即可。
  • 从卡片开始的需求用这张卡片，不另建卡片；项目没有指定执行方式时默认只做研发。
  • 在 Paseo 中打开需求会话可以看到整个过程。

升级须知 ​

  • 需要在对接配置中加上 query（读卡片）和 describe（改描述），写法见《项目定制与运行规则》"从卡片开始需求"。不用这个功能的，什么都不用改。
  • 行为变化："只做研发"的需求在研发完成时，发给外部系统对接的事件由 completed 改为 phase_done（"研发完成，待测试"）。给 phase_done 配了状态的，这类需求的卡片会改为那个状态，而不是"完成"对应的状态。
  • 功能目录新增 source.json、card-source.md、card-ai.md（只在从卡片开始的需求中）；本机新增 ~/.req-kit/cards/。状态文件格式不变。设计决定见 ADR 0029。

1.9.1 ​

1.9 的正式版（1.9.0 的发布任务因一个测试的时序问题失败，没有发布到 npm，内容相同，以 1.9.1 发布）。汇总 1.9.0-beta.1 到 beta.3 的全部内容（各节见下）：本机的需求索引与使用统计、Paseo 插件、外部系统对接。

使用者会看到的变化 ​

  • 使用统计：req stats 看本机的需求数、交付周期、返工、等待时长、用时和用量；--report 生成给管理方的汇总和明细，--export / --merge 汇总多台机器。
  • Paseo 插件（req plugin install）：在 Paseo 的网页端、桌面版和手机上查看本机所有需求的进度、文档（按 Markdown 显示）和统计，确认方案、停止、继续、开始测试验证、同步到外部系统。可以设为只读。
  • 外部系统对接：配置 integrations 后，需求在团队的需求管理系统中自动建卡、跟着阶段改状态；卡片字段在确认需求说明时整理。req integration test 预演命令，req sync 补发。
  • req api：给程序用的 JSON 接口，插件通过它工作。

升级须知 ​

  • 从 1.8.0 升级：依次看下面 1.9.0-beta.1 到 beta.3 的升级须知。三项新能力都是可选的；升级后在项目目录运行一次 req index --rebuild，让之前运行过的需求出现在索引和插件中。
  • 装过插件的，req upgrade 会自动把插件换成 1.9.1。
  • 从 1.9.0-beta.3 升级：功能没有变化，只改了版本号和文档中的版本示例。

1.9.0-beta.3 ​

外部系统对接：需求在团队的需求管理系统中自动建卡、跟着阶段改状态；插件中的文档按 Markdown 显示。

使用者会看到的变化 ​

  • 外部系统对接：配置 integrations 后，流水线开始时在需求管理系统中建一张卡，之后每到一个阶段改卡片的状态：开始开发、等待确认、研发完成、开始测试验证、完成、中断，对应哪个状态可以配置。卡片编号和链接显示在进度、完成报告和 Paseo 插件里。
    • 对接的是本机已有的命令行工具，命令的写法写在团队配置里，换系统或系统改参数都不用升级 req-kit。
    • 卡片的业务字段（优先级、需求类型等）由 AI 在确认需求说明时从需求说明中整理，和需求方一起确认后写进 card.json。
    • 外部系统出错不影响流水线：失败的调用会自动补发，也可以运行 req sync <需求>，插件中有"同步到外部系统"。
    • req integration test [需求] 显示每个事件会执行的完整命令，但不真正调用，配置时先用它检查。
  • 插件：文档按 Markdown 显示（标题、列表、表格、代码、链接），decisions.tsv 等显示为表格；需求详情中显示外部系统的卡片和链接。

升级须知 ​

  • 对接是可选的，写法见《项目定制与运行规则》的"外部系统对接"。integrations 只能写在本机或团队配置中；项目可以在自己的配置中用 integrationDefaults 提供项目编号等取值。
  • 状态文件新增可选字段 external，功能目录新增 card.json，格式版本仍为 1。
  • 自定义了 prompts.local/ 的不受影响；/req 的新需求手册在确认前多一步"卡片字段"，没有配置对接时自动跳过。设计决定见 ADR 0028。

1.9.0-beta.2 ​

Paseo 插件：在 Paseo 的界面里查看和管理需求。

使用者会看到的变化 ​

  • req-kit 插件（req plugin install）：在 Paseo 的网页端、桌面版和手机上都能用。
    • 侧边栏的"需求"：本机所有项目的需求，按"需要你处理、进行中、待测试验证、最近完成"分组，带待处理的数量。
    • 需求详情：每一步的状态、用时和结论（点开进入那个步骤的 agent）、质量门、联合需求的各仓库、用量；可以读需求说明、方案、确认预览、提测说明、完成报告等。
    • 确认方案、停止、继续、开始测试验证：每个都要再确认一次，做的事与终端里的 req 命令完全相同。
    • 每个工作区头部的"需求"按钮和面板、步骤 agent 输入框旁的"需求"按钮、使用统计页、Ctrl+K 中的"需求总览"。
    • 插件设置中可以打开"只读"，给只看不操作的人用。
  • 安装脚本最后询问是否安装插件（--with-plugin 直接安装，--no-plugin 不问；PowerShell 用 $ReqKitPlugin）。
  • 修正：安装脚本判断 Paseo 网页界面是否已开启时，读错了 paseo daemon config get 的输出（"已设置"被当成"已开启"）。

升级须知 ​

  • 插件是可选的。安装时会询问是否打开 Paseo 的插件总开关（pluginsEnabled）：插件是不受沙箱限制的代码；req-kit 插件只运行本机的 req api，不连接外部服务。
  • 装过插件后，req setup、req upgrade、req use 会自动把插件换成启用的版本。插件随 req-kit 一起发布，不需要单独的 npm 包。
  • 需要 Paseo 0.11。1.9 之前运行过的需求，先在项目目录运行一次 req index --rebuild。设计决定见 ADR 0027。

1.9.0-beta.1 ​

1.9 的基础：本机知道自己有哪些需求，记下每次运行的用时和用量，并给程序一个稳定的读取接口。插件（beta.2）和外部系统集成（beta.3）都建在它上面。

使用者会看到的变化 ​

1.8.0-beta.1 ​

研发流程按需求类型分流，代码检查由流水线自己把关，大需求按切片实现。

使用者会看到的变化 ​

  • 需求类型：/req 复述需求时会确认它是哪一类，流水线按类型走不同的做法：
    • 缺陷：先复现、找到根因再修。第一步改为"复现与定位"，先提交一个修复前失败的复现测试，写 diagnosis.md；复现不了就暂停，把需要你补充的信息发回对话。修复要让复现转绿，评审会实际确认。
    • 重构：先用测试锁住现有行为，再小步改动；评审首先看行为有没有变。
    • 评估：只调研、写评估报告（assessment.md），由另一个模型审阅，不写代码、不做验证；报告附需求草稿，可以接着说"按评估结果提一个新需求"。
  • 质量门：项目配置了检查命令时，流水线在写代码和修复的步骤之后自己运行 lint、类型检查、测试、构建。改动前通过、现在失败的，发回那一步的 agent 修复（最多 2 次）；仍然失败的交给代码评审和报告，报告结论最高为"有遗留问题"。进度查询会显示质量门的结果。
  • 按切片实现：标准档的方案分成几个能单独验证的切片时，代码实现逐片进行，每片一个新的 agent、各自提交和检查；子 agent 列表中显示为"5-代码实现 第2/3片"，中断后只重做当前片。
  • 范围检查：代码评审前比对方案列出的文件和实际改动的文件，清单之外的改动由评审逐一说明理由；评审新增"影响面"一节，只把影响正确性、安全、数据和验收的问题提为必须修改，避免越改越复杂。
  • 多模块与关联仓库：检查可以只在对应模块有改动时运行；其他仓库（例如前端项目的后端）可以登记为关联仓库，各步骤只读参考，不用猜接口。

升级须知 ​

  • 在项目主目录的对话中再运行一次 /req-setup：它会把实际跑通的检查命令写进 .requirement-pipeline.json 的 checks，并询问关联仓库。不运行也能用，只是没有质量门，/req-doctor 会提醒。
  • 新配置（都有默认值）：checks、qualityGate（fixAttempts 2、timeoutMinutes 20）、slices（profiles 标准档、max 6）、requirementTypes（缺陷、重构、评估）、relatedRepos。spec 头部的 - 类型： 由引擎读取（之前只给人看）：已有 spec 中写着"缺陷"的，继续时会按缺陷的做法进行。
  • 结果文件新增可选字段：方案设计的 slices、files、reproduced、questions，方案修订的 slices、files。状态文件新增可选字段 type、codeBase、gate，格式版本仍为 1。回滚到 1.7 后旧引擎忽略它们；按切片实现中断的需求，旧引擎会把实现整个重做一遍。
  • 自定义了 prompts.local/ 的：新增 types/defect.md、types/refactor.md、types/assessment.md、related-repos.md；00-shared-context.md、03-design.md、04-design-review.md、04b-design-revise.md、05-implement.md、06-code-review.md、07-review-fix.md、10-defect-fix.md、11-report.md 有增补，覆盖过它们的请对照合并。
  • 有质量门的项目，每次尝试开始时多一次检查运行，写代码的步骤之后各多一次；检查要能在几分钟内跑完。
  • 评估：新增用例 text-utils-rounding-defect（缺陷类型，检查先复现再修）。设计决定见 ADR 0023。

1.6.0-beta.1 ​

调度：预约开始、等待提醒、中断后自动继续、排队，以及需求总览。

使用者会看到的变化 ​

  • 预约开始：确认需求后可以说"今晚 10 点开始"或"明天早上开始"。流水线用 Paseo 定时任务预约，到时在这个对话里自动执行启动命令；在那之前修改需求说明也没关系。查看进度能看到预约，说"先停一下"即可取消。
  • 等待提醒：方案审核提出需要你决定的问题后，如果 24 小时内没有回答，会在对话里提醒一次（waitingReminderHours）。
  • 中断后自动继续：因限流、网络中断等临时错误中断（已自动重试过）时，预约 30 分钟后在对话里自动继续，每次尝试最多 2 次（autoResumeMinutes、autoResumeMax）。中断通知会写明预约的时间；说"先停一下"可以取消。
  • 排队：可以限制一台机器上同时运行的流水线数量（maxConcurrentPipelines，默认不限）。满了的时候新的需求会排队，并在对话里说明前面在跑哪些；轮到时自动开始。查看进度会显示"排队中"。
  • 定时检查（可选，默认关闭）：开启 watchdogMinutes 后，运行期间对话会定时检查一次，发现后台进程意外退出（例如机器重启）时自动继续。
  • 需求总览：req digest 列出项目中的需求，按"需要处理、待验收、开发中、对齐中、已验收"分组；req digest --notify 发到外部通知（如企业 IM，新的事件类型 digest）；req digest --schedule "0 9 * * 1" 让 Paseo 每周一 9 点自动发送。

升级须知 ​

  • 新的可选配置：maxConcurrentPipelines（0）、queuePollSeconds（60）、waitingReminderHours（24）、autoResumeMinutes（30）、autoResumeMax（2）、watchdogMinutes（0）。提醒和自动继续默认开启，不需要时设为 0。现有配置无需改动。
  • 新的启动参数 --at；新命令 req digest。
  • 外部通知新增事件类型 digest。通知模块配置了 events 列表的不会收到它；没有配置 events 的会收到，按 contracts/notifier-event.md 的约定，模块应忽略不认识的类型（模板已处理）。
  • 状态文件增加可选字段 schedules、autoResumes、queuedSince（格式版本仍为 1）。
  • 这些功能使用 Paseo 的定时任务（经由内部客户端，见 ADR 0020）；Paseo 不支持时自动关闭，并在输出中说明。
  • 设计决定见 ADR 0020。

使用者会看到的变化 ​

  • 需求变更后增量继续：修改需求、回答了方案审核的问题、验收不通过后继续开发时，在已有方案和代码的基础上只处理变化的部分（方案追加"第 N 次尝试"一节，评审只看本次的改动，验证重点验变化的验收标准并回归其余的），通常比第一次快很多。要完全从零开始仍用 --restart。

  • 配置向导：req configure（或 node install.mjs --configure）列出 Paseo 中可用的 agent、模型，自动选择不需要确认的运行模式，几个选择题即可写好配置，不再需要手工编辑 JSON。
  • 一键升级：req upgrade 下载最新版本、安装依赖并切换；req upgrade 1.3.0 指定版本；req upgrade --check 只看有没有新版本。/req-doctor 会提示有新版本。
  • 外部通知接口：可以在"需要你决定""等待批准""开发中断""已完成"和进展时刻，调用本机的通知模块，例如转发到企业内部 IM。req-kit 只提供接口和模板（notifiers/im-template.mjs），具体发送由使用方实现；req notify-test 发测试消息。
