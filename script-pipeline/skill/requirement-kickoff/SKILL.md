# 需求对齐与需求说明（流水线第 1、2 步）

用户的初始描述：$ARGUMENTS

（如果上面显示的是占位符本身或为空，以用户在本次消息中给出的描述为准。）

## 你在做什么，为谁做

对面是一位懂业务、不写代码的同事。他们知道自己想解决什么问题，但不熟悉技术词汇，也不知道哪些细节会影响实现。你的任务分两步：

1. 通过对话把需求谈到"换一个人来做，也会做出同一个东西"的清晰程度。
2. 把谈定的内容写成一份需求说明文件 `spec.md`。

这份 spec 之后会交给一条无人值守的自动化流水线（方案设计 → 审核 → 实现 → 评审 → 验证 → 报告）。流水线里没有人能再回头问用户，所以**现在没问清楚的地方，后面只能靠猜**。这是这一步值得花时间的原因。

## 开始前：确认工作区

每个需求最好在自己独立的 worktree 工作区中进行：开发流水线会在这个对话的工作目录里运行几个小时并提交代码；独立的工作区不会影响项目的主目录，几个需求也可以同时进行。

先运行 `git rev-parse --git-dir --git-common-dir` 和 `git branch --show-current`：

- **两个路径相同（主目录）**：用白话告诉用户上面的好处，建议在 Paseo 中为这个需求新建一个工作区再开始：点 **New workspace**，选择这个项目，**Isolation** 选 **New worktree**，起点选 `origin/main`，然后在新工作区里重新输入需求。用户想在这里继续也可以，按下面"确定功能目录"之后的第 4 点新建功能分支。
- **两个路径不同（已经在 worktree 中）**：直接继续，使用当前分支，不要再新建分支。
- **不是 git 仓库**：直接继续，跳过所有分支相关的操作。

整个对话过程中不要切换工作目录或分支。

## 开始前：先自己看，再开口问

1. 读项目里已有的说明：`CONTEXT.md`（业务术语表）、`docs/adr/`（已做的决定）、`README`、`CLAUDE.md` / `AGENTS.md`、`.requirement-pipeline/project-notes.md`（本项目对需求开发的补充约定，如有），以及与这个需求相关的代码。能从代码和文档里得到答案的事情，不要拿去问用户。
2. 依次加载 `grilling` 和 `domain-modeling` 两个 skill，并按它们的方法进行访谈和记录。这正是 `/grill-with-docs` 所做的事（它本身只允许用户手动触发，所以这里直接加载它的两个组成部分）。有 Skill 工具时用它加载；没有时（例如 Pi），直接读取这两个 skill 的 `SKILL.md`，它们和本 skill 安装在同一个 skill 目录下（例如 `~/.agents/skills/grilling/SKILL.md`）。如果两个 skill 都找不到，停下来告诉用户需要先安装：`npx skills add mattpocock/skills -g --copy`，不要用自己的理解替代。
3. 确定功能目录：`docs/features/<YYYYMMDD>-<英文短名>/`，例如 `docs/features/20261012-sms-login/`。英文短名用小写字母和连字符。创建该目录。
4. 只有在主目录中进行、且当前在默认分支（如 `main`、`master`）上时，才新建并切换到分支 `feature/<功能目录名>`（例如 `feature/20261012-sms-login`）。不要动工作区里已有的、与本需求无关的改动。流水线不会在默认分支上提交代码。

## 判断规模，选择档位

用户讲完需求、你复述并得到确认后，判断这次需求的规模，向用户推荐一个档位，说明理由，请用户确认：

- **快速档**：小改动，影响面窄，不涉及数据结构、权限、计费或对外接口。例如改文案或样式、加一个配置项、调整一个字段的显示。访谈只需问清：要改什么、改成什么样、不改什么、怎么算做对了。之后的开发流程每个环节只做一轮，通常更快完成。
- **标准档**：其他情况，按下面完整的访谈方式进行。

拿不准时选标准档。访谈中发现需求比预想的复杂（涉及数据、权限、多个角色或流程），改为标准档并告诉用户。

## 访谈方式：在 grilling 的基础上，全程使用业务语言

`grilling` 规定了怎么追问（沿着决策树逐项问到底、一次一个问题、给出推荐答案）。在此之上遵守下面的约定。它们的共同出发点是：用户只能可靠地回答业务问题，技术问题问了也只会得到猜测。

**先听，再复述。** 请用户用自己的话把想要的东西讲一遍。然后用两三句话复述你的理解，得到确认后再往下问。

**问结果，不问手段。** 问"提交之后，谁应该在多久之内看到这条记录"，不问"要不要用消息队列"。数据库、接口、字段类型、框架、同步还是异步，这些都由你来决定，记入"技术假设"，留给方案设计阶段。

**必须提到技术限制时，翻译成业务后果。** 不说"这需要改表结构"，而说"这样做的话，以前的历史订单不会带上这个信息，只有新订单才有。可以接受吗？"

**用具体例子提问。** "假设张三周五下午 6 点提交了申请，而审批人周一才上班，这期间张三看到的状态是什么？"比"审批超时怎么处理"更容易回答，答案也更准。

**让用户做选择题。** 每个问题给出 2–4 个选项，把你推荐的放在第一个并说明理由。如果当前环境有选择题式的提问工具就用它，否则用带编号的文字选项。用户说"你定"时，采用推荐项并把它记为假设。

**追问到目的。** 用户说"加一个导出按钮"时，问清楚导出之后拿去做什么。常常会发现真正的需求是另一件事。

**主动问那些用户想不到的情况。** 正常流程用户会自己讲，下面这些通常要你来提：
- 出错和中断：填错了、提交到一半关掉了、重复提交了
- 反悔：能不能撤销、修改、删除，谁可以
- 权限：谁能看、谁能改、谁不能看
- 边界：数量上限、时间期限、为空的情况
- 已有的数据和正在进行中的业务怎么办
- 这次明确不做什么

**每条需求都问"怎么算做对了"。** 得到一个可以实际检查的答案，它会成为验收标准。

**控制节奏。** 每谈完一个主题，用一两句话小结"已经定了什么、还剩什么"。发现用户的说法与现有文档或系统行为矛盾时，直接指出来并请他们选择。

## 边谈边记

在功能目录下维护 `alignment.md`，每定下一件事就追加一条，不要等到最后再回忆：

```markdown
## <主题>
- 问题：<用业务语言描述的问题>
- 结论：<定下来的答案>
- 理由 / 被否的选项：<一句话>
- 来源：用户明确确认 / 用户说"你定"（记为假设）/ 从现有代码或文档得出
```

术语和重要决定按 `domain-modeling` 的做法写入 `CONTEXT.md` 和 `docs/adr/`。

## 什么时候可以结束访谈

快速档：要改什么、改成什么样、不改什么、每条验收标准，都有了结论。

标准档：下面每一项都有了结论，或被明确标为"假设"或"本次不做"：

- 要解决的问题，以及做成之后怎么衡量
- 谁会用，在什么场景下用
- 主流程的每一步
- 业务规则（计算方式、状态变化、限制条件）
- 出错、反悔、权限、边界、历史数据
- 本次不做的范围
- 每条需求的验收标准
- 优先级：哪些必须有，哪些可以以后再说

如果还有只有用户能回答、且答错会导致做错东西的问题，继续问，不要带着它进入下一步。

## 第 2 步：写 spec

1. 按同目录下的 `spec-template.md` 的结构，把 `alignment.md` 的内容整理成 `<功能目录>/spec.md`，并在顶部写明档位（`- 档位：快速` 或 `- 档位：标准`），流水线据此决定走哪一档。快速档可以省略与这次改动无关的章节。
2. 写作要求：
   - 用业务语言，只写"要什么"和"怎么算做对"，不写"怎么实现"。技术上的想法只进入"技术假设"一节。
   - 每条功能需求有编号（FR-1、FR-2…），每条验收标准有编号（AC-1.1、AC-1.2…）。后续的设计、测试和报告都会引用这些编号。
   - 验收标准用"在什么情况下 / 当用户做了什么 / 应该看到什么"的形式，写到一个没参加过这次对话的人也能据此判断通过与否的程度。
   - 没谈到的内容不要自己补。需要补的，回去问用户，或写进"假设"并说明依据。
3. 写完后自查一遍，发现问题就改：
   - 每条 FR 至少有一条可以实际检查的 AC
   - 异常和边界情况都有对应的 AC，而不是只有正常流程
   - 没有"快速""友好""合理"这类无法检查的词，除非给出了具体标准
   - 各条需求之间没有互相矛盾
   - "待确认问题"一节为空。如果不为空，回去问用户
4. 给用户一份 10 行以内的白话摘要：会做什么、不做什么、有哪些假设需要他们知情。请他们确认。
5. 用户确认后，把 spec 顶部的状态改为"已确认"并填上日期（保持 `- 状态：已确认（<日期>）` 这个写法，流水线靠这一行判断 spec 已确认）。如果是 git 仓库，把功能目录、`CONTEXT.md` 和 `docs/adr/` 中本次的改动提交到当前功能分支（只提交这些文件，不要 push）。

用户不确认、或者提出修改时，回到访谈，改完再走一遍第 3–5 步。没有用户确认的 spec 不要标为"已确认"。

## 第 3 步起：启动开发流水线

spec 确认后，告诉用户需求说明保存在哪里，然后问用户是否现在开始开发。说明三点：开发在后台进行，通常需要几个小时；过程中不需要他们盯着；完成或需要他们做决定时，会在这个对话里通知。

用户同意后，在当前工作目录执行（`<功能目录>` 换成实际路径，例如 `docs/features/20261012-sms-login`）：

```
node "{{PIPELINE_LAUNCHER}}" --feature <功能目录>
```

这条命令在 bash、PowerShell、cmd 中写法相同。它会自动识别当前对话（Paseo 提供的 `PASEO_AGENT_ID`、`PASEO_AGENT_CWD`），不需要另外传对话 ID 或仓库目录。

流水线会把这个对话的工作目录当作仓库目录，每个步骤都作为子 agent 挂在这个对话下、在同一个目录中工作。所以：
- 只为当前对话所在的项目启动流水线。需求属于其他项目时，请用户到那个项目中新开对话。
- 整个对话过程中不要切换工作目录（不要 `cd` 到别的目录再执行命令），功能目录也必须建在当前工作目录之内。

这个命令会检查条件后在后台启动流水线，一两秒内返回：

- 输出"已在后台启动"：告诉用户开发已经开始。每个步骤会以"[功能目录名] 步骤名"的名字出现在这个对话的子 agent 列表里，想看进展可以点开。
- 输出"未启动"：把原因用白话告诉用户。原因是 spec 未确认时，回到上面的确认步骤；原因是同一目录已有流水线在运行时，告诉用户需要等它结束；原因是工作目录不一致时，告诉用户需要到需求所在的项目中开对话；其他原因（找不到工具、配置有误等）请用户联系技术同事，并附上输出内容。

用户没有同意时，告诉他们之后随时可以说"开始开发"，再执行上面的命令。

## 查看进度、暂停

用户问"做到哪了""进展怎么样"时，执行：

```
node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --status
```

把输出用一两句白话转告用户：现在在做什么、已经完成了哪些、大概进行了多久。

用户要求暂停或停止时，先确认一次（停止后当前步骤做到一半的工作不会保留），确认后执行：

```
node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --stop
```

告诉用户已经停下，之后说"继续开发"即可从停下的步骤接着做。那时执行：

```
node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --resume
```

## 收到流水线通知时

流水线会把消息发进这个对话，开头是"【需求开发流水线通知】"。这些消息不是用户发的。收到时：

1. 用业务语言把要点转告用户，不要原样粘贴，除非用户要求。
2. 按通知中的说明处理：
   - **进展**（标题带"进展"）：用一句话转告即可，例如"方案已经定了，开始写代码"。
   - **需要业务决定**：用本 skill 的访谈方式逐个向用户提问，把答案记入 `alignment.md` 并更新 `spec.md`，请用户再次确认 spec，然后执行通知中给出的继续命令。
   - **等待权限批准**：告诉用户打开通知中提到的 agent 处理批准。
   - **流水线中断**：说明发生了什么，请用户联系技术同事；问题解决后执行通知中给出的继续命令。
   - **流水线结束**：转告结论和摘要，读一下功能目录中的 `report.md`，提醒用户"需要你做的事"。用户追问细节时，以 `report.md` 和功能目录中的其他文件为准来回答。
3. 通知到达时如果你正在和用户谈别的事，先把当前这句话说完，再转告通知内容。
