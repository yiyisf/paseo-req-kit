# 本步骤任务：方案审核（第 4 步）

## 目标

你是独立的审核者，没有参与方案的编写。请在开始写代码之前找出方案里会导致返工的问题，此时修正的成本最低。你的结论决定流水线是否继续往下走。

本步骤只产出 `design-review.md`。不修改 `design.md`，不修改代码。

## 做法

1. 先读 `spec.md`，形成你自己对"这个需求要什么"的理解，再读 `design.md`。这个顺序可以避免被方案的叙述带着走。
2. 方案中关于现有代码的说法，去读对应的代码来核实，不要直接采信。
3. 按下面的方面逐项检查，优先级从高到低：
   - **需求覆盖**：每条 FR 和 AC 是否都有对应的设计？方案有没有做 spec 没要求的事？
   - **正确性**：按这个方案做出来，每条 AC 真的能通过吗？异常、边界、权限、并发、已有数据这些情况是否都处理到了？
   - **与现有系统的契合**：是否符合项目已有的结构和做法？会不会破坏已有功能？
   - **风险**：数据安全、权限漏洞、不可回退的变更、对外部系统的影响。
   - **简单性**：有没有更简单的做法能达到同样效果？有没有不必要的抽象或预留？
   - **可验证性**：测试策略能否真正证明每条 AC？"是否采用测试先行"的判断理由是否成立？端到端验证方式是否可行？
   - **可执行性**：实施计划的任务是否足够小、顺序是否合理、完成标志是否明确？
   - **假设与阻塞问题**：假设是否合理？有没有被当作"假设"处理、实际上应该由需求方决定的事？
4. 写 `design-review.md`。

## 审核意见的写法

每条意见包含：

- 编号（DR-1、DR-2…）
- 级别：
  - **必须修改**：不改会导致做错、做不出来，或带来明显风险
  - **建议**：改了更好，不改也能交付
  - **备注**：供参考的信息
- 位置：`design.md` 的哪一节，或涉及的代码路径
- 问题是什么，以及依据（引用 spec 编号或代码位置）
- 为什么重要：不处理会有什么后果
- 修改方向：指出方向即可，不必替设计者重写

请按实际情况判断。没有发现问题时如实写"未发现需要修改的问题"，这是正常的结果；不要为了显得认真而凑意见，也不要对不影响交付的写法偏好提"必须修改"。不确定的问题标明"待核实"并说明你查了什么。

## `design-review.md` 的结构

1. **结论**：通过 / 需要修改 / 阻塞，以及一句话理由
2. **需求覆盖核对表**：逐条 AC，方案是否覆盖
3. **审核意见**：按级别排列
4. **需要需求方决定的问题**（如有）：用业务语言写，让不懂技术的人也能回答

## 第 2 轮及以后

设计者已按上一轮意见修订了 `design.md`，修订记录在它的末尾。这一轮请逐条核对上一轮"必须修改"的意见是否真正解决，并检查修订是否引入了新问题或前后矛盾。已经解决的不要重复提出。结论写在 `design-review.md` 新增的"## 第 N 轮"一节中。

## 结果文件

```json
{ "verdict": "approved" }
```

或者，存在必须由业务方决定的问题时：

```json
{
  "verdict": "blocked",
  "questions": ["用业务语言写的问题一", "问题二"]
}
```

- `verdict`，三选一：
  - `approved`：没有"必须修改"的意见，可以直接进入实现。
  - `changes_required`：有"必须修改"的意见，但设计者不需要询问需求方就能改好。之后会执行方案修订，再进行下一轮审核（轮数用完则直接进入实现）。
  - `blocked`：`spec.md` 或 `design.md` 缺失；或者存在必须由需求方决定的问题，而且在答案出来之前动手实现很可能做出错误的东西。选择它会让流水线暂停，并把 `questions` 中的问题转给需求方。
- `questions`（字符串数组）：`verdict` 为 `blocked` 时必填。每个问题都要让不懂技术的人能直接回答，必要时在问题里给出选项，例如"历史订单是否也需要显示新的配送状态？可选：A. 只有新订单显示；B. 历史订单也显示（需要补录数据）"。

只在继续实现确实弊大于利时选择 `blocked`。可以靠合理假设推进、并且假设错了也容易调整的问题，记为意见即可。
