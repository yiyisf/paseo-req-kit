# 本步骤任务：服务启动验证（第 8 步，在项目有常驻服务时执行）

## 目标

确认带着这次改动的服务能够正常启动，并留下一份准确的启动方法，供下一步的功能验证使用。

下一步由另一个 agent 在新的会话中执行，你启动的进程不会保留到那时。所以这一步要交付的是两样东西：**"能否启动"的结论**，和**一份照着做就能启动的方法**。结束前请把你启动的进程关掉。

## 做法

1. 读 `design.md` 的"运行方式"一节，以及项目的 `README`、启动脚本和配置样例。如果项目定义了 Paseo 工作区脚本（`paseo.json`）并且你有对应的工具，可以用它来启动。
2. 准备本地运行环境：
   - 安装项目依赖（只装在项目目录内）。
   - 用项目提供的样例配置生成本地配置。数据库、缓存等依赖使用本地实例或测试实例。
   - 这次改动包含数据结构变更时，只在本地或测试数据库上执行。
3. 在后台启动服务，把输出保存到日志文件。
4. 等待服务就绪。用明确的信号来判断（健康检查接口返回成功、日志出现启动完成的标志、端口开始监听），并设定超时时间。不要只靠等待固定的秒数。
5. 启动之后检查：
   - 启动日志里有没有报错，或者这次改动带来的新警告。
   - 访问一个最基本的入口（首页、健康检查接口，或一个不依赖本次功能的已有接口），确认服务确实在响应。
   - 访问一个与本次功能相关的入口，确认它已经加载。这里只确认它存在，功能是否正确留给下一步验证。
6. 关闭服务，确认进程已经退出、端口已经释放。
7. 写 `service-start.md`。

## 启动失败时

先看日志找出原因，再决定怎么处理：

- **由这次的代码改动引起**（语法错误、配置项缺失、依赖没有声明、迁移脚本有问题等）：做最小的修复，重新启动验证，提交修复，并把问题和修复方式记录下来。
- **由环境引起**（缺少某个本地服务、缺少凭据、端口被占用等）：能在仓库范围内安全解决的就解决（例如换一个空闲端口）；解决不了的，准确记录缺什么、在哪一步失败、报错内容是什么。不要为了让服务启动而连接生产环境，或者屏蔽报错。
- 使用基线提交也同样启动不了，说明问题不是这次改动造成的，把这一点记录清楚。

## `service-start.md` 的内容

1. **结论**：启动成功 / 启动失败 / 无法判断，以及一句话说明
2. **环境准备**：需要的依赖服务、配置文件、一次性的准备命令
3. **启动命令**：可以直接复制执行的完整命令，以及执行所在的目录
4. **就绪判断**：怎么知道服务已经启动好（检查的地址或日志标志，通常需要等多久）
5. **访问地址**：服务地址和端口，以及与本次功能相关的入口
6. **停止方法**
7. **启动日志摘录**：关键的几行，有报错时附上完整的报错
8. **发现的问题和处理**：没有就写"无"

## 完成标准

- 结论来自你的实际启动。
- 启动命令是你实际执行并且成功的那一条。
- 你启动的进程都已经关闭。

## 结果文件

```json
{ "started": true }
```

- `started`（布尔值）：带着这次改动的服务成功启动并能响应请求时为 `true`，否则为 `false`。为 `false` 时流水线仍会继续，由功能验证决定哪些内容无法验证。
