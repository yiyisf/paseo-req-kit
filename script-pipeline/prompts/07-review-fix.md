# 本步骤任务：评审问题修复（第 7 步，在代码评审结论为"需要修改"时执行）

## 目标

处理 `code-review.md` 中的评审意见，让代码达到可以进入功能验证的状态。修复之后通常还有一轮代码评审来核对你的处理；轮数用完时，功能验证会直接在你的修复结果上进行。所以每条意见的处理结果要记录清楚。

## 做法

1. 读 `spec.md`、`design.md`、`implementation.md` 和 `code-review.md`。
2. 逐条处理"阻塞"和"重要"级别的意见：
   - 先确认问题成立：读相关代码，能复现的先复现。
   - 修复产生问题的原因，而不是只让报告的那个现象消失。检查同样的问题是否在别处也存在。
   - 合适的时候为它补一个测试：修复前会失败，修复后通过。
   - 核实后如果认为某条意见不成立，不要直接跳过。写明依据（代码位置、spec 编号或实际运行结果）。
3. "建议"级别的意见：改动小、风险低、确实更好的就处理；其余的记录为不处理并说明原因。
4. 修复不能改变 spec 要求的行为，也不要借机做评审意见之外的改动。
5. 全部处理完后，运行完整的测试、代码检查、类型检查和构建，确认没有引入新的失败。
6. 在 `code-review.md` 中最新一轮评审的"处理记录"小节填写下表。评审者写的内容保持原样，只追加：

   | 意见编号 | 级别 | 处理结果（已修复 / 不成立 / 未处理） | 提交号 | 说明 |
   | --- | --- | --- | --- | --- |

   并在表后写明修复之后实际运行的检查命令和结果。

**修不了的情况**：某条"阻塞"或"重要"意见经过合理尝试仍无法修复时，标为"未处理"，写明原因和已经尝试的做法。它会被带进最终报告。不要用绕过检查的方式让它看起来已经解决。

## 完成标准

- 每条评审意见都出现在处理记录里。
- 完整测试的结果来自你在最后一次改动之后的实际运行。
- 工作区里没有遗留本步骤产生的未提交改动。

## 结果文件

```json
{ "status": "done" }
```

- `status`：所有"阻塞"和"重要"意见都已处理（修复或说明了不成立的依据）时为 `"done"`；有意见未处理时为 `"partial"`。
