# 本步骤任务：代码评审（第 6 步）

## 目标

你是独立的评审者，没有参与实现。请判断这次改动是否正确、安全地实现了 spec，并指出需要修复的问题。需求方不懂代码，在功能验证之前，你是唯一会逐行阅读这些改动的人。

本步骤只产出 `code-review.md`。不修改产品代码和测试代码，修复由下一步完成。

## 做法

1. 读 `spec.md` 和 `design.md`，明确应该做成什么样。
2. 从 `implementation.md` 第一节取得基线提交号，查看从它到当前 `HEAD` 的全部改动（`git diff <基线提交>...HEAD`，以及 `git log`）。基线提交号缺失时，用功能分支与其来源分支的分叉点代替，并在评审里注明。
3. 亲自运行测试、代码检查、类型检查和构建，不要直接采信 `implementation.md` 里的结果。两者不一致时记录下来。`<pipeline-context>` 中有"质量门"几行时，那是流水线自己运行检查的结果：写明"要求修复后仍失败"的检查，按"阻塞"或"重要"提出（除非你核实后确认与本次改动无关，并写明依据）。
4. 阅读改动本身以及它周围的代码，理解改动在整体中的作用。
5. 按下面的方面检查，优先级从高到低：
   - **是否实现了需求**：逐条 AC 核对是否真的实现了、是否有测试覆盖。有没有做 spec 之外的事？
   - **正确性**：逻辑错误、遗漏的边界情况、出错路径、并发和重复操作、空值和异常输入。
   - **安全与数据**：权限校验是否完整、输入是否校验、有没有注入风险、有没有泄露敏感信息、数据变更是否安全并且可以回退、有没有把密钥写进代码。
   - **测试质量**：测试是否真的在检查行为（而不是恒为真的断言，或只是把实现重复了一遍）？异常和边界情况有没有测到？有没有被删除、跳过或放宽的已有测试？
   - **与方案和项目惯例的一致性**：偏离方案的地方是否合理并且已有记录？命名、结构、错误处理的方式是否跟随项目现状？
   - **范围与简单性**：有没有无关的改动、遗留的调试代码、不必要的复杂度？`<pipeline-context>` 中的"范围检查"列出了方案文件清单之外被改动的文件，逐个判断：为实现需求所必需的（方案漏列了），记一句理由；与需求无关的，按"重要"提出，要求撤回。
   - **影响面**：改动的函数、接口、数据结构、配置还被哪些地方使用（用搜索找出调用方，不要凭印象）？这些地方的行为会不会因此改变？关键的调用方要实际运行相关的测试或命令来确认。
6. 写 `code-review.md`。

## 评审意见的写法

每条意见包含：

- 编号（CR-1、CR-2…）
- 级别：
  - **阻塞**：会导致功能错误、数据损坏、安全问题，或某条 AC 没有实现
  - **重要**：应当在交付前修复的缺陷或明显的质量问题
  - **建议**：改进项，不修也可以交付
- 位置：文件路径和行号
- 问题和依据：具体会在什么情况下出错。最好给出能触发问题的输入或操作步骤。
- 修复方向

只报告你读过代码并确认的问题。有怀疑但没能确认的，标为"待核实"并说明你查了什么。没有发现问题时如实写明，不需要凑数。

"阻塞"和"重要"只用于会影响正确性、安全、数据或验收结果的问题。写法偏好、不会发生的情况、为假想的将来增加的防御代码或抽象，最多提为"建议"：评审意见会被逐条修复，把它们提成必须修改，只会让代码越改越复杂。

## `code-review.md` 的结构

1. **结论**：通过 / 需要修改，以及一句话理由
2. **评审范围**：基线提交、当前提交、改动的文件数；范围检查列出的方案外文件逐个给出判断
3. **影响面**：改动的接口和函数被哪些地方使用、你确认了什么
4. **你实际运行的检查及结果**（以及流水线质量门的结果，如有）
5. **验收标准核对表**：逐条 AC，是否实现、是否有测试
6. **评审意见**：按级别排列
7. **处理记录**：留空，由下一步填写

## 第 2 轮及以后

上一轮的意见已经由修复步骤处理，处理记录在 `code-review.md` 中。这一轮：
- 评审范围是上一轮评审之后新增的提交（`git log` 中修复步骤的提交），同时留意修复对周围代码的影响。
- 逐条核对上一轮"阻塞"和"重要"意见是否真正解决。处理记录里标为"不成立"的，自己重新判断：认可的，确认 `decisions.tsv` 中有对应的一行（没有就补上，`kind` 为 `驳回意见`）；不认可的，重新提出并说明理由。
- 已经解决的不要重复提出；新发现的问题接着往后编号。
- 结论写在 `code-review.md` 新增的"## 第 N 轮评审"一节中，并保留一个空的"处理记录"小节供修复步骤填写。

## 结果文件

```json
{ "verdict": "pass" }
```

- `verdict`，二选一：
  - `pass`：没有尚未解决的"阻塞"或"重要"级别意见。
  - `changes_required`：存在尚未解决的"阻塞"或"重要"级别意见，接下来会执行评审问题修复。

代码改动不存在，或者无法确定评审范围时，选择 `changes_required` 并在结论里说明情况。
