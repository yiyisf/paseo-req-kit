# 本步骤任务：提测说明（研发阶段的最后一步，在代码评审之后执行）

## 目标

写一份提测说明 `handoff.md`，交给接下来做测试验证的人或 agent。读者可能是测试同事，也可能是之后另一个时间、另一个对话里启动的验证 agent，他们都没有看过研发过程。读完这份说明，他们应该知道：这次改了什么、怎么把它跑起来、哪些已经自测过、应该重点测什么、测试前要准备什么。

`<pipeline-context>` 中有"执行方式"一行时，按它理解这份说明的用途：

- **分阶段**：研发阶段到此结束，这份说明就是提测单。流水线会停下来，由人决定什么时候开始测试验证，可能是几个小时甚至几天之后。
- **只做研发**：流水线不做测试验证，测试由人按这份说明来做。
- 没有这一行（连续）：功能验证马上开始，这份说明是它的输入。

本步骤只写文档，不修改产品代码和测试代码。

## 做法

1. 读 `spec.md`、`design.md`、`implementation.md`、`code-review.md`（包括处理记录），以及 `decisions.tsv`。
2. 用 `git log` 和 `git diff` 确认实际的改动范围：工作分支、本需求的第一个提交和最后一个提交。增量继续时（`<pipeline-context>` 中有"增量继续"），写明本次开始时的提交之后的改动，并说明这是第几次提测、修了什么。
3. 核对"怎么跑起来"中的每一条：依赖安装、数据库迁移、配置项、启动命令。能在本地确认的就实际执行一遍确认命令可用，不能确认的标明"未在本地确认"。项目有 `paseo.json` 的，写出服务对应的脚本名。
4. 写 `handoff.md`，然后提交（只提交这个文件）。

## `handoff.md` 的结构

1. **这次改了什么**：按 FR 列出，每条一句话，用需求方能懂的话说。附上分支名和提交范围（起止提交）。
2. **怎么跑起来**：需要安装的依赖、数据库迁移、新增或修改的配置项（写配置名和用途，不写密钥的值）、启动命令或 `paseo.json` 中的脚本名、部署到测试环境时要注意的事项。
3. **自测结果**：单元测试和其他自动化检查的结果（数量、是否通过）；代码评审的结论和轮数；哪些 AC 已经有自动化测试覆盖（列出 AC 编号和对应的测试）。
4. **建议重点测试**：风险最高的 AC 及原因；可能受影响的已有功能（回归范围）；容易出问题的边界情况和异常路径。按优先级排序。
5. **已知问题和未完成项**：代码评审没有处理的意见、实现中没有完成的部分、已知的限制。没有就写"无"。
6. **测试需要的准备**：测试数据、测试账号、功能开关、外部服务的模拟。**只写在哪里取、怎么准备，不写口令、密钥本身。** 只能用于测试环境，不要写任何生产环境的地址或凭据。

篇幅以测试同事十分钟内能读完为准。档位为"快速"时，每节几句话即可。

## 完成标准

- 六节都在；没有内容的写"无"。
- 提交范围和自测结果来自你实际运行的命令，不是照抄前面的记录。
- `handoff.md` 已提交，工作区里没有本步骤产生的未提交改动。

## 结果文件

```json
{ "status": "done" }
```

- `status`：六节都写完时为 `"done"`；有无法确认的内容（例如启动命令没能在本地确认）时为 `"partial"`，并在 `handoff.md` 中标明。
