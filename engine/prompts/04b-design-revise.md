# 本步骤任务：方案修订（第 4 步的后续，在审核结论为"需要修改"时执行）

## 目标

根据 `design-review.md` 的审核意见修订 `design.md`，让下一步的实现者拿到一份可以直接执行的方案。修订之后可能还有一轮审核，也可能因为轮数用完而直接进入实现；无论哪种情况，审核者和实现者都会对照你的修订记录，所以每条意见是怎么处理的要写清楚。

本步骤不写产品代码，不修改 `design-review.md`。

## 做法

1. 读 `spec.md`、`design.md`、`design-review.md`。
2. 逐条处理审核意见：
   - **必须修改**：先去读相关代码或 spec，确认问题成立，然后修改方案。修改时检查受影响的其他章节（需求对照表、实施计划、测试策略）并一并更新，保持方案前后一致。
   - 如果核实后你认为某条"必须修改"不成立，不要直接忽略。写明你的依据（代码位置或 spec 编号），并在两种做法中选择更稳妥的那一种。
   - **建议**：采纳成本低且确实更好的就采纳；不采纳的写明原因。
3. 在 `design.md` 末尾新增"修订记录（第 N 轮）"一节，N 与你处理的那一轮审核一致：

   | 意见编号 | 级别 | 处理结果（已修改 / 部分采纳 / 未采纳） | 说明，以及改动了哪些章节 |
   | --- | --- | --- | --- |

4. 有 `preview.md` 或 `prototype/` 时，方案改动涉及的部分同步修改，保持与 `design.md` 一致；`ui_change` 的判断变了的，在结果文件中写上新的值。
5. 审核中提出的"需要需求方决定的问题"，原样保留在方案的"阻塞问题"或"假设"一节中，写明你暂时采用的处理方式。最终报告会把它们交给需求方。

## 完成标准

- 每条"必须修改"和"建议"都出现在修订记录里。
- 修订后的方案自身没有矛盾，每条 AC 仍然都有着落。

## 结果文件

```json
{ "status": "done" }
```

修订改变了实施计划的切片或改动的文件清单时，把新的完整列表写上（写法与方案设计步骤的结果文件相同），流水线以最新的为准；没有变化时省略：

```json
{ "status": "done", "slices": ["S1 …（AC-1.1）", "S2 …（AC-2.1）"], "files": ["src/auth/", "test/auth/"] }
```

- `status`：所有"必须修改"的意见都已处理（修改或说明了不采纳的依据）时为 `"done"`；有意见没能处理时为 `"partial"`，并在修订记录中说明。
