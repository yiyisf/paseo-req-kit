# 这次是需求变更后的继续

`<pipeline-context>` 中有"增量继续"一行，说明这个需求之前已经做过一轮（方案，可能还有代码），之后需求说明被修改了：需求方改了需求、回答了方案审核提出的问题，或者验收时发现了问题。这一次**在已有工作的基础上只处理变化的部分**，不要推倒重来。

先了解变了什么：

- 读 `changes.md` 的最后一节（变更内容、原因），再对照 `spec.md` 当前版本。没有 `changes.md` 时，用 `git log -p -- <功能目录>/spec.md` 查看 spec 最近的改动。
- 方案审核提出过问题的，读 `design-review.md` 最后一轮的问题和 `alignment.md` 中对应的回答。
- 验收发现问题的，读 `acceptance.md` 中"不通过的处理"。
- 测试验证退回的（增量继续的原因写着"测试验证发现缺陷"），读 `changes.md` 最后的"测试验证退回"一节和 `verification.md` 最后一轮的缺陷清单。这一次只修这些缺陷：方案设计写修复计划，代码实现逐个修复并补测试，最后重新写 `handoff.md`（追加"第 N 次提测"一节，说明修了哪些缺陷）。

各步骤的做法：

- **方案设计**：保留仍然成立的部分，在 `design.md` 末尾追加"## 第 N 次尝试：需求变更"一节，写明变化点、受影响的 FR/AC、对已有代码的改动计划（改哪些、新增哪些、哪些不动），以及需要补充或修改的测试。原有内容中已经不成立的地方，就地标注"（第 N 次尝试起不再适用，见下文）"，不要整篇重写。
- **方案审核**：重点审核变化部分是否完整、是否与没变的部分冲突。
- **代码实现**：在现有代码上修改，只动与变化相关的部分；已有的、仍然正确的实现和测试保留。在 `implementation.md` 末尾追加本次的记录。
- **代码评审**：评审范围是"本次开始时的提交"之后的改动（`git diff <该提交>..HEAD`），同时确认这些改动没有破坏之前已经通过评审的部分。
- **功能验证**：变化涉及的 AC 全部重新验证；其余 AC 至少跑一遍现有的自动化测试，确认没有回退。
- **完成报告**：在开头说明这是第几次尝试、因为什么变化，验收对照表中标出哪些 AC 是这次新增或修改的。

上一次没有写过代码时（`<pipeline-context>` 中"上一次是否已经写过代码：否"），实现类步骤按正常方式进行，只是方案设计要在已有的 `design.md` 基础上修订。
