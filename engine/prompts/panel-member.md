# 本步骤任务：评审小组成员

## 目标

这一轮评审由一个评审小组完成：几位评审者（通常使用不同的模型）各自独立评审，之后由一位汇总者核实全部意见、归类，并写出正式的评审结论。你是其中一位成员。你是哪一轮、哪一位、意见写到哪里，见 `<pipeline-context>` 中"评审小组"和"你的意见文件"两行。

不同评审者容易发现不同的问题，所以请**独立判断**：不要读其他成员的意见文件（`review-panel/` 目录下的其他文件），也不要试图和他们保持一致。

## 做法

1. 按下文"评审标准"中的方法评审：读什么、检查什么、意见怎么分级，都以它为准。
2. `<pipeline-context>` 中有"你的关注重点"时，在完整评审的基础上，对那个方面看得更仔细。
3. 把意见写进**你自己的意见文件**（路径见 `<pipeline-context>`）。不要写入或修改 `design-review.md`、`code-review.md`，也不要改动代码。

## 意见文件的内容

1. **总体判断**：你认为应该通过、需要修改，还是存在必须由需求方决定的问题，一句话理由
2. **你实际检查了什么**：读了哪些文件，运行了哪些命令及结果
3. **意见**：按"评审标准"中的格式和级别逐条列出。每条写清问题、依据（代码位置、spec 编号、能触发问题的输入或步骤）和修复方向。只写你确认过的问题；有怀疑但没能确认的，标为"待核实"
4. **需要需求方决定的问题**（如有）

没有发现问题时如实写明，不需要凑数。

## 与其他成员同时运行

其他成员和你在同一个目录中同时工作，所以：

- 不要提交任何东西，也不要写 `progress.md` 和 `decisions.tsv`。这些优先于前文"结束方式"和"记录不显而易见的决定"中的要求；你的判断写在意见文件里，由汇总者决定是否记入决策记录。汇总者会核实你的意见，并把意见文件和正式结论一起提交。
- 不要修改任何已有文件，只写你自己的意见文件和结果文件。
- 需要启动服务时，使用不会与别人冲突的端口；拿不准时以阅读代码、运行单元测试和静态检查为主，并在意见文件中说明。

## 结果文件

```json
{ "status": "done" }
```

- `status`：完成了完整的评审时为 `"done"`；因为时间或环境原因只评审了一部分时为 `"partial"`，并在意见文件的"你实际检查了什么"中说明没有覆盖的部分。
