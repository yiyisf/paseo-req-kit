# 本步骤任务：需求说明审阅（在需求方确认之前）

## 与上文不同的地方

这一步不在开发流水线之中。需求方和对话里的 AI 刚写好一份需求说明**草稿**，还没有确认；你是请来的第二双眼睛，帮他们在确认之前找出问题。所以：

- 上文中"spec 已确认、是唯一依据、不要修改"仍然适用：**不要修改** `spec.md`、`alignment.md` 或任何其他文件，只写下面的审阅文件和结果文件。
- 不要提交任何东西，不要写 `progress.md` 和 `decisions.tsv`。这些优先于上文"结束方式"和"记录不显而易见的决定"的要求。
- 不要改代码，也不要开始设计方案。

## 目标

找出会让开发做错、做不完、或者没法判断是否做对的地方，把每一个都写成需求方能直接回答的问题。你的读者是有技术背景、但不读代码的需求方（测试、产品经理、项目经理）。

## 做法

1. 读 `spec.md`、`alignment.md`（访谈记录）、`changes.md`（如有）。`<pipeline-context>` 中给出了需求说明的写法清单，按它逐项对照。
2. 读与需求相关的现有代码、接口、数据结构和测试，确认需求说明中对"现状"的描述是否属实。
3. 逐项检查：
   - **歧义**：同一句话能理解成两种做法，而两种做法结果不同。
   - **遗漏**：异常和边界情况（输入为空、超长、重复提交、并发、超时、外部服务失败）、权限（谁能做、谁不能）、已有数据怎么处理、和已有功能的关系。
   - **验收标准能否验证**：每条 AC 是否写清前置条件、操作和预期结果，预期结果是否具体到可以判断对错（"提示友好"这类说法不行）。
   - **冲突**：FR 之间、FR 与 AC 之间、与访谈记录、与现有系统行为之间的矛盾。
   - **范围**：写进来但与目标无关的内容，或者为了达到目标显然还需要、却没有写的内容。
4. 只报告真正会影响结果的问题。措辞、格式之类的小问题最多列三条，放在最后。

## 审阅文件

写到功能目录下的 `spec-review.md`（已存在时覆盖），内容：

1. **结论**：可以确认 / 建议先澄清 N 个问题，一句话说明
2. **问题**：按重要程度排序，每条包括：
   - 编号（Q1、Q2……）和涉及的位置（FR/AC 编号或章节）
   - 问题是什么，为什么重要（不澄清会导致什么）
   - **给需求方的问题**：写成选择题，2–4 个选项，标出推荐项和理由
3. **核对过的现状**：你实际读了哪些代码、接口，与需求说明一致还是不一致
4. **小问题**（可选，最多三条）

## 结果文件

```json
{ "verdict": "issues", "issues": ["Q1 验证码过期后再次提交的提示没有写明（AC-1.3）", "Q2 ……"] }
```

- `verdict`：没有需要澄清的问题时为 `"ready"`；否则为 `"issues"`。
- `issues`：`verdict` 为 `"issues"` 时必填，每条一句话，与审阅文件中的问题一一对应。
