# 不靠看图检查网页界面

`<pipeline-context>` 中有"界面检查命令"一行时，涉及网页界面的验收标准，除了按操作步骤核对结果，还要用这个命令检查页面**看起来**有没有问题。它用本机的 Edge 或 Chrome 打开页面，按电脑和手机两种宽度，用文字报告：文字显示不全、互相遮挡、超出屏幕、图片没加载、文字太淡、输入框和按钮没有名字、控制台报错、请求失败；给了原型时，还会拿原型里的标题、按钮、字段名、表头和页面逐项对文字。不需要看截图。

1. 每个涉及界面的页面或状态运行一次，例如：
   ```
   <界面检查命令> http://127.0.0.1:3000/orders --prototype <功能目录>/prototype/list.html --state 正常 --shots <功能目录>/.pipeline/ui
   ```
   - 要先操作才能看到的状态（查询结果、空数据、出错），把操作写进一个 JSON 文件用 `--steps` 传入，例如 `[{"fill":["#keyword","不存在的订单"]},{"click":"text=查询"},{"wait":"text=暂无订单"}]`（选择器是 Playwright 的写法：`text=…`、`#id`、`role=button[name="查询"]`）。
   - 原型中用 `data-state` 画了几种状态的，`--state` 写对应的状态名，每种状态各检查一次。
   - 需要登录的页面：用项目的测试账号和测试环境，把登录操作写进 `--steps`；没有测试账号时，在产物中说明哪些页面没能检查。
2. 逐条判断报告的内容。有的是故意的设计（例如故意截断的长文本带有完整提示），写明理由后不算缺陷；其余按缺陷处理，在 `verification.md` 中记下报告原文的那一行和页面地址。"原型里有、页面上没有"的文字，先确认是不是需求方确认过要有的内容。
3. 截图保存在 `--shots` 目录，是给人看的：**不要再把截图读进对话**，它对判断帮助不大，还很费 token。

命令打不开浏览器（这台机器没有 Edge 或 Chrome，或者装驱动失败）时，不要反复重试，在产物中写明"界面检查没能进行"和命令的输出，改用接口调用、项目自带的端到端测试等方式验证。
