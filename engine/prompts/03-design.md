# 本步骤任务：方案设计（第 3 步）

## 目标

把已确认的 spec 变成一份技术方案 `design.md`。衡量标准是：一个没看过任何对话、只读了 `spec.md` 和 `design.md` 的工程师，可以不问任何问题就开始实现，并且做出来的东西能通过 spec 里的每一条验收标准。

本步骤不写产品代码。代码由下一个 agent 按你的计划来写。

## 做法

1. 通读 `spec.md` 和 `alignment.md`。`alignment.md` 记录了每个决定的理由，能帮你理解 spec 背后的意图。
2. 调研代码库，直到能具体回答下面几个问题（写下文件路径作为依据）：
   - 这个需求会涉及哪些模块、数据和接口？
   - 项目里类似的功能是怎么做的？哪些可以直接复用？
   - 项目怎么运行、怎么测试？实际执行一次现有的测试、类型检查和构建命令，记录基线结果。后面的步骤需要用它来区分"原来就失败"和"这次改坏的"。
3. 设计满足 spec 的最简单方案。优先沿用项目已有的模式；不为 spec 没有提出的将来需求做预留。如果确实存在值得认真比较的另一种做法，简要写明取舍；没有就不必硬凑。
4. 把方案拆成可以独立完成、独立验证的小任务，排好顺序。
5. 写 `design.md`。

## `design.md` 的内容

1. **需求理解**：用一段话说明这个需求要达成什么。
2. **需求对照表**：spec 中每条 FR 和 AC，对应方案里的哪一部分。每条 AC 都要有着落；方案里也不应有对不上任何需求的部分。
3. **现状**：相关的模块和文件（带路径）、会复用的现有做法。
4. **方案**：数据的变化、接口和交互的变化、关键流程、出错时的处理、权限控制、对已有数据和已有功能的兼容。写到实现者不需要再做设计决定的程度。
5. **影响范围与风险**：会碰到哪些已有功能，可能出什么问题，怎么回退。
6. **实施计划**：按顺序列出任务。每个任务写明要改或新建的文件、完成的标志、对应的 AC。
7. **测试策略**：
   - 项目现有的测试方式、运行命令和基线结果。
   - 本需求是否适合测试先行（TDD），并给出理由。适合的情况：项目已有可用的测试框架，并且要改的是可以单独测试的逻辑。不适合的情况：例如纯配置或样式调整、项目没有任何测试基础、改动主要是胶水代码而测试成本远高于收益。不适合时，写明用什么方式替代验证。可以对不同任务给出不同结论。
   - 测试用例清单：每条 AC 用什么测试覆盖（单元、集成，还是端到端）。
   - 端到端验证方式：项目是否已有端到端测试工具；没有的话，用什么方式从用户入口把关键流程走一遍（页面操作、接口调用、命令行调用）。
8. **运行方式**：这个项目是否有需要启动起来才能验证的常驻服务（Web 服务、API、后台进程等）。有的话写明启动命令、依赖的本地服务、端口、怎么判断启动成功。库、脚本、一次性命令行工具这类不需要常驻进程的项目，写"无常驻服务"。
9. **假设**：你按最合理的理解定下来、但 spec 没有明说的事。
10. **阻塞问题**：只有需求方能回答、猜错会做出错误东西的问题。没有就写"无"。有阻塞问题时，仍然把能确定的部分设计完整。
11. **影响摘要**：用 3–6 句话说明，做完之后使用者会看到什么变化、什么不会变。可以提到接口、页面、字段这类需求方熟悉的东西，但不讲代码结构。这段话会被最终报告引用。

## 完成标准

- 每条 AC 在需求对照表和测试用例清单里都能找到。
- 方案中关于现有代码的每个说法，你都实际读过对应的代码。
- 基线测试结果来自你的实际运行。

## 结果文件

```json
{ "has_runnable_service": true }
```

- `has_runnable_service`（布尔值）：项目有需要启动才能验证的常驻服务时为 `true`，否则为 `false`。它决定后面是否执行"服务启动验证"这一步。
