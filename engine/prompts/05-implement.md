# 本步骤任务：代码实现（第 5 步）

## 目标

按照 `design.md` 的实施计划完成代码，使 spec 中的每条验收标准都得到实现，并有相应的测试或其他验证方式作为依据。

## 开始前

1. 读 `spec.md`、`design.md`（包括末尾的"修订记录"，如有）和 `design-review.md`。
2. 记下基线提交：执行 `git rev-parse HEAD`，把结果写进 `implementation.md` 的第一行。之后的代码评审会从这个提交开始比较，所以要在改动任何代码之前记录。
3. 运行一次现有测试，确认与 `design.md` 记录的基线一致。不一致时把差异记下来再继续。

## 做法

按实施计划的顺序逐个任务完成。

**方案判断该任务适合测试先行时**，按红、绿、重构的节奏进行：
1. 先写测试，用它表达对应验收标准所要求的行为。
2. 运行测试，确认它失败，而且失败的原因是功能尚未实现，而不是测试本身写错了。
3. 写出能让测试通过的最少代码。
4. 测试通过后整理代码，保持测试通过。

**方案判断该任务不适合测试先行时**，不要硬套。按方案指定的替代方式验证，并把验证过程记录下来。

实现过程中如果发现方案对测试先行的判断与实际不符（比如实际上很容易测，或者实际上测不了），按实际情况调整，并在"与方案的偏离"里说明。

无论采用哪种方式：

- 测试检查的是对外可见的行为和结果，不是内部实现细节。这样的测试在以后重构时仍然有效。
- 写出对所有合理输入都正确的通用实现。不要只让测试用例里的那几个值通过。
- 不要为了通过而删除、跳过或放宽已有测试。如果某个已有测试失败是因为 spec 要求的行为确实变了，更新它，并在 `implementation.md` 里写明改了哪个测试、对应哪条需求。
- 每完成一个任务，运行相关测试，通过后提交一次。
- 发现方案有错或行不通时，可以偏离方案，选择仍然满足 spec 的做法，并记录原因。偏离不能改变 spec 要求的行为。
- 临时文件、调试输出、试验性代码在结束前清理掉。

全部任务完成后，运行完整的测试、代码检查、类型检查和构建（项目有哪些就运行哪些），处理本次改动引入的问题。

**流水线会复查。** 本步骤结束后，流水线会自己运行项目配置的检查（质量门：格式、lint、类型检查、测试、构建，以项目配置为准），只看改动之前通过、现在失败的项。有这样的项，会把输出发回给你修复。所以结束前先自己把这些检查跑一遍；改动之前就失败的检查不算你的问题，但要在产物里如实写明。

**做不下去时**：某个任务经过合理尝试仍然无法完成，停止在那里，如实记录做到了哪一步、卡在哪里、试过什么。保留已经完成并且测试通过的部分。不要用占位实现、写死的返回值或跳过的测试让它看起来已经完成。

## `implementation.md` 的内容

1. **基线提交**：改动前的提交号
2. **任务完成情况**：

   | 任务 | 状态（完成 / 部分完成 / 未完成） | 对应 AC | 提交号 | 说明 |
   | --- | --- | --- | --- | --- |

3. **改动清单**：新建和修改的文件，每个一句话说明
4. **验收标准与测试对照**：每条 AC 由哪个测试或哪种验证方式覆盖
5. **测试与检查结果**：实际运行的命令和结果摘要（通过和失败的数量，失败项的名称）
6. **与方案的偏离**：哪里没有按方案做，原因是什么
7. **未完成事项和已知问题**：没有就写"无"

## 完成标准

- 计划中的任务都已完成，或者未完成的部分已如实记录。
- 完整测试的结果来自你在最后一次改动之后的实际运行。
- 工作区里没有遗留本步骤产生的未提交改动。

## 结果文件

```json
{ "status": "done" }
```

- `status`：计划中的任务全部完成时为 `"done"`；有任务未完成或部分完成时为 `"partial"`，并在 `implementation.md` 中说明。
