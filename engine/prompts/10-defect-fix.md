# 本步骤任务：测试缺陷修复（第 10 步，在功能验证或复验发现缺陷时执行）

## 目标

修复 `verification.md` 中登记的、尚未解决的缺陷，使对应的验收标准能够达成。修复完成后，会有另一个 agent 独立复验你的结果。

第 2 轮及以后，要处理的是上一轮复验后仍未解决的缺陷，以及复验中新发现的问题，见 `verification.md` 最新一轮"复验结果"中的"遗留问题汇总"。

## 做法

1. 读 `spec.md`、`design.md`、`implementation.md` 和 `verification.md`。
2. 按严重程度从高到低处理"严重"和"一般"级别的缺陷。对每一个缺陷：
   - **先复现。** 按复现步骤操作，亲眼看到问题。复现不了时，不要凭猜测修改代码，记录你的操作和看到的结果。
   - **找到原因。** 弄清楚为什么会这样，而不是只让报告的那个现象消失。检查同样的原因是否还会在别处造成问题。
   - **先补测试，再修复。** 条件允许时，先写一个能重现这个缺陷的测试，看到它失败，再去修复，直到它通过。
   - **修复要通用。** 不要针对验证用的特定输入做特殊处理，也不要通过修改或删除验证者的测试来让它通过。
   - **核对 spec。** 修复之后的行为必须与 spec 一致。如果发现这个"缺陷"其实是测试写错了，或者 spec 本身有两种合理的理解，不要改动产品行为去迁就测试。记录你的依据，交给复验和报告处理。
3. "轻微"级别的缺陷：改动小、风险低的就一并修复；其余的记录为未处理。
4. 全部处理完后，运行完整的测试、代码检查、类型检查和构建，确认修复没有破坏其他功能。流水线随后也会自己运行项目配置的检查，改动之前通过、现在失败的会发回给你修复。
5. 在 `verification.md` 末尾追加"## 缺陷处理记录（第 N 轮）"一节，填写下表。验证者写的内容保持原样，只追加：

   | 缺陷编号 | 严重程度 | 处理结果（已修复 / 不是缺陷 / 无法复现 / 未修复） | 原因 | 修复方式 | 提交号 |
   | --- | --- | --- | --- | --- | --- |

   并在表后写明修复之后实际运行的检查命令和结果。

**修不了的情况**：经过合理尝试仍无法修复的缺陷，标为"未修复"，写明已经查明的原因和尝试过的做法。它会被带进最终报告，由人来决定下一步。这比一个看起来通过、实际没有解决的修复要好。

## 完成标准

- 每个缺陷都出现在处理记录里。
- 完整测试的结果来自你在最后一次改动之后的实际运行。
- 你启动的进程都已经关闭，工作区里没有遗留本步骤产生的未提交改动。

## 结果文件

```json
{ "status": "done" }
```

- `status`：本轮要处理的"严重"和"一般"缺陷都已处理（修复，或说明了不是缺陷 / 无法复现的依据）时为 `"done"`；有缺陷未修复时为 `"partial"`。
