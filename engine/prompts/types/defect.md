# 本需求类型的做法：缺陷修复

这个需求是修复一个缺陷：spec 描述了现象、复现步骤和修复后应有的行为。缺陷修复的关键是**先证明问题存在、找到原因，再修**。没有复现就动手修，等于在猜。

## 所有步骤

- "复现"指一个能稳定重现问题的自动化测试，或者一个可以重复执行的复现脚本（命令、接口调用），修复前失败、修复后通过。它是这个需求最重要的证据，各步骤都围绕它来做和查。
- 只修这个缺陷和它的根因。看到别处有不相关的问题，记下来交给人决定；同一个根因在别处造成的问题，修在同一处的一并修好并写明。

## 复现与定位（design）

本步骤代替通常的方案设计，产出 `diagnosis.md` 和一份简短的 `design.md`。

1. 按 spec 中的复现步骤，在本地实际重现问题。先写成自动化测试（项目有测试框架时首选）；写不了测试的，写成复现脚本，放在测试目录或功能目录的 `repro/` 下。运行它，确认它**失败，并且失败的方式与 spec 描述的现象一致**（而不是因为测试本身写错）。
2. 缩小范围：找到最小的触发条件，排除其他可能的原因（数据、配置、环境）。
3. 定位根因：读代码、加临时日志、查提交历史（`git log -p`、`git bisect`），直到能用代码位置说清楚"为什么会这样"。临时的日志和调试代码用完删掉。
4. 判断影响面：同样的原因还会在哪里造成问题；已有的错误数据是否需要修正（spec 没有提到的，写进阻塞问题或假设）。
5. 提交复现测试或脚本。这时它是失败的，提交信息注明"复现，修复前失败"。

`diagnosis.md` 的内容：现象与复现（复现测试或脚本的位置、运行命令、失败输出的摘要）、根因（带代码位置）、排除了哪些其他原因、影响面、修复思路。

`design.md` 按通常的结构写，但可以简短：修复方案、改动的文件、实施计划（通常一片）、测试策略（复现测试，加上相邻的、不应受影响的行为）。

**复现不了时**：按 spec 的步骤和合理的变化尝试过，仍然重现不了，不要猜着改代码。在 `diagnosis.md` 中写明你尝试了什么、看到了什么，然后在结果文件中写 `"reproduced": false`，在 `questions` 中写需要需求方补充的信息，具体到能直接回答的程度（例如"出错时用的是哪种账号？大约几点操作的？"）。流水线会暂停，把这些问题转给需求方。

结果文件在通常的字段之外加上 `reproduced`：

```json
{ "has_runnable_service": true, "reproduced": true, "files": ["src/order/price.ts", "test/order/price.test.ts"] }
```

## 方案审核（design_review）

重点审核 `diagnosis.md`：复现是否真的对应 spec 描述的现象；根因有没有代码上的依据，还是只是猜测；修复针对的是根因，还是只让这个现象消失；影响面是否查过。复现或根因站不住的，提为"必须修改"。

## 代码实现（implement）

- 复现测试已经由上一步提交。先运行它，确认仍然失败，再修复，直到它通过。
- 不要修改复现测试的断言来让它通过。确实写错了的，在 `implementation.md` 中说明改了什么、为什么。
- 为影响面中提到的相关情况补测试。

## 代码评审（code_review）

额外核对：
- 复现测试在修复前确实失败、修复后通过：检出修复前的提交（或用 `git stash`）实际运行一次，不要只看记录。
- 修复针对的是 `diagnosis.md` 中的根因；同一个根因造成的其他问题是否处理或记录。
- 复现测试的断言在修复过程中有没有被放宽。

## 功能验证（verify）

按 spec 的复现步骤从用户入口重做一遍，确认现象消失；再验证相邻的、不应受影响的行为。在 `verification.md` 中写明复现步骤修复前后的对比。

## 完成报告（report）

用需求方能懂的话说明：问题是什么原因造成的、修了什么、怎么确认修好了（复现步骤修复前后的结果）、有没有同类问题或需要修正的数据。
