# 本需求类型的做法：评估

这个需求是一次调研评估：spec 列出了要回答的问题（能不能做、怎么做、影响多大、大概要多少工作量）。**只读，不写代码**：不修改产品代码、测试和配置，功能目录之外不提交任何文件。流程是调研评估 → 评估审阅 ⇄ 评估修订 → 评估报告，没有代码实现、代码评审和验证。

## 所有步骤

- 结论要有依据：引用代码位置（文件和行号）、实际运行的命令和输出、文档链接。推测要标明是推测。
- 可以运行只读的命令（运行测试、构建、查看依赖、在本地启动服务看看），不做会留下改动的操作，启动的进程用完关掉。需要写一次性的试验代码来回答问题时，写在功能目录的 `spike/` 下，不改项目代码。

## 调研评估（design）

本步骤写 `assessment.md`，不写 `design.md`。结构：

1. **结论摘要**：逐条回答 spec 中的问题，各一两句话
2. **现状**：相关的模块、数据、接口，带代码位置
3. **可选方案**：两到三种（只有一种合理做法时就写一种）。每种写做法、优点、风险、影响到的模块和功能、大致工作量（按"小 / 中 / 大"给，并列出主要的工作项，不编造精确的人天）
4. **推荐**：推荐哪一种、为什么、前提条件
5. **风险与未知**：哪些还不确定，要怎样才能确定
6. **如果要做**：把推荐方案写成需求草稿（标题、要做的事、建议的验收标准），可以直接作为下一个需求的起点

结果文件中 `has_runnable_service` 写 `false`，不需要 `slices` 和 `files`。

## 评估审阅（design_review）

你审阅的是 `assessment.md`，不是技术方案：逐条核实其中关于代码的说法（读对应的代码）；结论是否回答了 spec 中的每个问题；方案比较是否公平、风险有没有遗漏；工作量的判断有没有依据。意见按"必须修改 / 建议 / 备注"写进 `design-review.md`，结论和结果文件的规则不变。

## 评估修订（design_revise）

按审阅意见修订 `assessment.md`（不是 `design.md`），在它的末尾追加修订记录。

## 评估报告（report）

`report.md` 是给需求方的评估结论，不按"验收对照"的结构写：

1. **结论**：逐条回答 spec 中的问题
2. **推荐的做法**和理由；其他做法为什么没选
3. **风险**和还不确定的事
4. **如果决定要做**：下一步怎么走（需求草稿在 `assessment.md` 最后一节；在对话里说"按评估结果提一个新需求"即可开始）
5. **附录**：调研中实际运行的命令、引用的代码位置、审阅经过了几轮、用时与用量

结果文件的 `outcome`：问题都有了有依据的回答时写 `completed`；部分问题没能回答时写 `completed_with_issues`；评估没有完成时写 `not_completed`。
