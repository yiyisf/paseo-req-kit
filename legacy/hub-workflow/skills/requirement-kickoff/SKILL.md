# 需求对齐与需求说明（流水线第 1、2 步）

用户的初始描述：$ARGUMENTS

## 你在做什么，为谁做

对面是一位懂业务、不写代码的同事。他们知道自己想解决什么问题，但不熟悉技术词汇，也不知道哪些细节会影响实现。你的任务分两步：

1. 通过对话把需求谈到"换一个人来做，也会做出同一个东西"的清晰程度。
2. 把谈定的内容写成一份需求说明文件 `spec.md`。

这份 spec 之后会交给一条无人值守的自动化流水线（方案设计 → 审核 → 实现 → 评审 → 验证 → 报告）。流水线里没有人能再回头问用户，所以**现在没问清楚的地方，后面只能靠猜**。这是这一步值得花时间的原因。

## 开始前：先自己看，再开口问

1. 读项目里已有的说明：`CONTEXT.md`（业务术语表）、`docs/adr/`（已做的决定）、`README`、`CLAUDE.md` / `AGENTS.md`，以及与这个需求相关的代码。能从代码和文档里得到答案的事情，不要拿去问用户。
2. 用 Skill 工具依次加载 `grilling` 和 `domain-modeling` 两个 skill，并按它们的方法进行访谈和记录。这正是 `/grill-with-docs` 所做的事（它本身只允许用户手动触发，所以这里直接加载它的两个组成部分）。如果这两个 skill 加载不了，停下来告诉用户需要先安装：`npx skills add mattpocock/skills`，不要用自己的理解替代。
3. 确定功能目录：`docs/features/<YYYYMMDD>-<英文短名>/`，例如 `docs/features/20261012-sms-login/`。英文短名用小写字母和连字符。创建该目录。
4. 如果这是一个 git 仓库：新建并切换到分支 `feature/<功能目录名>`（例如 `feature/20261012-sms-login`）。不要动工作区里已有的、与本需求无关的改动。

## 访谈方式：在 grilling 的基础上，全程使用业务语言

`grilling` 规定了怎么追问（沿着决策树逐项问到底、一次一个问题、给出推荐答案）。在此之上遵守下面的约定。它们的共同出发点是：用户只能可靠地回答业务问题，技术问题问了也只会得到猜测。

**先听，再复述。** 请用户用自己的话把想要的东西讲一遍。然后用两三句话复述你的理解，得到确认后再往下问。

**问结果，不问手段。** 问"提交之后，谁应该在多久之内看到这条记录"，不问"要不要用消息队列"。数据库、接口、字段类型、框架、同步还是异步，这些都由你来决定，记入"技术假设"，留给方案设计阶段。

**必须提到技术限制时，翻译成业务后果。** 不说"这需要改表结构"，而说"这样做的话，以前的历史订单不会带上这个信息，只有新订单才有。可以接受吗？"

**用具体例子提问。** "假设张三周五下午 6 点提交了申请，而审批人周一才上班，这期间张三看到的状态是什么？"比"审批超时怎么处理"更容易回答，答案也更准。

**让用户做选择题。** 每个问题给出 2–4 个选项，把你推荐的放在第一个并说明理由。如果当前环境有选择题式的提问工具就用它，否则用带编号的文字选项。用户说"你定"时，采用推荐项并把它记为假设。

**追问到目的。** 用户说"加一个导出按钮"时，问清楚导出之后拿去做什么。常常会发现真正的需求是另一件事。

**主动问那些用户想不到的情况。** 正常流程用户会自己讲，下面这些通常要你来提：
- 出错和中断：填错了、提交到一半关掉了、重复提交了
- 反悔：能不能撤销、修改、删除，谁可以
- 权限：谁能看、谁能改、谁不能看
- 边界：数量上限、时间期限、为空的情况
- 已有的数据和正在进行中的业务怎么办
- 这次明确不做什么

**每条需求都问"怎么算做对了"。** 得到一个可以实际检查的答案，它会成为验收标准。

**控制节奏。** 每谈完一个主题，用一两句话小结"已经定了什么、还剩什么"。发现用户的说法与现有文档或系统行为矛盾时，直接指出来并请他们选择。

## 边谈边记

在功能目录下维护 `alignment.md`，每定下一件事就追加一条，不要等到最后再回忆：

```markdown
## <主题>
- 问题：<用业务语言描述的问题>
- 结论：<定下来的答案>
- 理由 / 被否的选项：<一句话>
- 来源：用户明确确认 / 用户说"你定"（记为假设）/ 从现有代码或文档得出
```

术语和重要决定按 `domain-modeling` 的做法写入 `CONTEXT.md` 和 `docs/adr/`。

## 什么时候可以结束访谈

下面每一项都有了结论，或被明确标为"假设"或"本次不做"：

- 要解决的问题，以及做成之后怎么衡量
- 谁会用，在什么场景下用
- 主流程的每一步
- 业务规则（计算方式、状态变化、限制条件）
- 出错、反悔、权限、边界、历史数据
- 本次不做的范围
- 每条需求的验收标准
- 优先级：哪些必须有，哪些可以以后再说

如果还有只有用户能回答、且答错会导致做错东西的问题，继续问，不要带着它进入下一步。

## 第 2 步：写 spec

1. 按同目录下的 `spec-template.md` 的结构，把 `alignment.md` 的内容整理成 `<功能目录>/spec.md`。
2. 写作要求：
   - 用业务语言，只写"要什么"和"怎么算做对"，不写"怎么实现"。技术上的想法只进入"技术假设"一节。
   - 每条功能需求有编号（FR-1、FR-2…），每条验收标准有编号（AC-1.1、AC-1.2…）。后续的设计、测试和报告都会引用这些编号。
   - 验收标准用"在什么情况下 / 当用户做了什么 / 应该看到什么"的形式，写到一个没参加过这次对话的人也能据此判断通过与否的程度。
   - 没谈到的内容不要自己补。需要补的，回去问用户，或写进"假设"并说明依据。
3. 写完后自查一遍，发现问题就改：
   - 每条 FR 至少有一条可以实际检查的 AC
   - 异常和边界情况都有对应的 AC，而不是只有正常流程
   - 没有"快速""友好""合理"这类无法检查的词，除非给出了具体标准
   - 各条需求之间没有互相矛盾
   - "待确认问题"一节为空。如果不为空，回去问用户
4. 给用户一份 10 行以内的白话摘要：会做什么、不做什么、有哪些假设需要他们知情。请他们确认。
5. 用户确认后，把 spec 顶部的状态改为"已确认"并填上日期。如果是 git 仓库，把功能目录、`CONTEXT.md` 和 `docs/adr/` 中本次的改动提交到当前功能分支（只提交这些文件，不要 push）。
6. 最后告诉用户：需求说明已保存在哪里，以及启动后续流水线时要填的内容就是功能目录的路径（例如 `docs/features/20261012-sms-login`）。

用户不确认、或者提出修改时，回到访谈，改完再走一遍第 3–5 步。没有用户确认的 spec 不要标为"已确认"。
