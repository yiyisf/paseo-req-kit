# 需求说明（spec）

spec 是开发流水线判断"要做什么"的唯一依据。流水线的每一步都会引用它的编号（FR-n、AC-n.m），最终报告也按它逐条对照。

## 写

1. 按模板 `{{REQ_KIT_ROOT}}/skills/spec-writing/spec-template.md` 的结构，把 `alignment.md` 的内容整理成 `<功能目录>/spec.md`。
2. 填好顶部的几行。流水线只读其中三行，写法要保持原样：
   - `- 状态：草稿`（确认后改为 `- 状态：已确认（<日期>）`）
   - `- 档位：标准` 或 `- 档位：快速`
   - `- 执行方式：分阶段` 或 `- 执行方式：只做研发`：只在用户选了这两种时写；连续（默认）不写这一行
   其余几行（类型、版本、格式）给人和 `/req` 看。新需求的版本是 1，每次修改需求加 1。
3. 快速档可以省略与这次改动无关的章节，但"范围""功能需求与验收标准""假设"必须有。
4. 写作要求：
   - 只写"要什么"和"怎么算做对"，不写"怎么实现"。技术上的想法只进入"技术假设"一节。
   - 每条功能需求有编号（FR-1、FR-2…），每条验收标准有编号（AC-1.1、AC-1.2…），写法见 `acceptance-criteria`（`{{REQ_KIT_ROOT}}/skills/acceptance-criteria/SKILL.md`）。
   - 没谈到的内容不要自己补。需要补的，回去问，或写进"假设"并说明依据。
   - 术语与仓库的 `GLOSSARY.md` 一致。

## 自查

写完后逐项检查，发现问题就改：

- 每条 FR 至少有一条可以实际检查的 AC
- 异常和边界情况都有对应的 AC，而不是只有正常流程
- 没有"快速""友好""合理"这类无法检查的词，除非给出了具体标准
- 各条需求之间没有互相矛盾
- "测试与验证"一节写明了测试数据和验证环境（快速档可以只写一句）
- "待确认问题"一节为空。不为空就回去问

## 确认

1. 给需求方一份 10 行以内的摘要：会做什么、不做什么、有哪些假设需要他们知情、他们之后会怎么验收。告诉他们完整文件的位置，愿意的话可以直接打开看。
2. 请他们确认。提出修改时，回到访谈，改完再自查、再确认。
3. 确认后，把顶部改为 `- 状态：已确认（<日期>）`。没有确认的 spec 不要标为"已确认"。
4. 如果是 git 仓库，把功能目录、`GLOSSARY.md` 和 `docs/adr/` 中本次的改动提交到当前分支。只提交这些文件，不 push。提交信息例如 `docs(<功能目录名>): 需求说明已确认`。
