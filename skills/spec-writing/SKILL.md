# 需求说明（spec）

spec 是开发流水线判断"要做什么"的唯一依据。流水线的每一步都会引用它的编号（FR-n、AC-n.m），最终报告也按它逐条对照。

## 写

1. 按模板 `{{REQ_KIT_ROOT}}/skills/spec-writing/spec-template.md` 的结构，把 `alignment.md` 的内容整理成 `<功能目录>/spec.md`。
2. 填好顶部的几行。流水线读其中四行，写法要保持原样：
   - `- 状态：草稿`（确认后改为 `- 状态：已确认（<日期>）`）
   - `- 档位：标准` 或 `- 档位：快速`
   - `- 类型：新需求` / `小改动` / `缺陷` / `重构` / `评估`：缺陷、重构、评估各有自己的开发做法（见下文"按类型的写法"）
   - `- 执行方式：分阶段` 或 `- 执行方式：只做研发`：只在用户选了这两种时写；连续（默认）不写这一行。评估不写
   其余几行（版本、格式）给人和 `/req` 看。新需求的版本是 1，每次修改需求加 1。
3. 快速档可以省略与这次改动无关的章节，但"范围""功能需求与验收标准""假设"必须有。
4. 写作要求：
   - 只写"要什么"和"怎么算做对"，不写"怎么实现"。技术上的想法只进入"技术假设"一节。
   - 每条功能需求有编号（FR-1、FR-2…），每条验收标准有编号（AC-1.1、AC-1.2…），写法见 `acceptance-criteria`（`{{REQ_KIT_ROOT}}/skills/acceptance-criteria/SKILL.md`）。
   - 没谈到的内容不要自己补。需要补的，回去问，或写进"假设"并说明依据。
   - 术语与仓库的 `GLOSSARY.md` 一致。

## 按类型的写法

模板按新需求写成。另外三种类型的重点不同，流水线也会按类型走不同的做法：

- **缺陷**：背景写现象、影响范围、从什么时候开始。必须有**复现步骤**：环境、账号或数据、操作、看到的结果、应有的结果。验收标准至少一条"按复现步骤操作，应该看到……"（修复前不通过、修复后通过），再加上相邻的、不应受影响的行为。流水线会先复现再修，复现不了会回来问，所以复现步骤越具体越好。
- **重构**：目标写改进什么，并且可以检查（例如"订单模块不再引用旧的支付库"）。第一条验收标准是**行为不变**：列出必须保持不变的主要行为（接口、页面、数据、导出的文件），然后是改进目标的验收标准。"本次不做"写明不顺带修改的行为。
- **评估**：功能需求写成**要回答的问题**（例如"FR-1 现有的订单接口能否支持按门店筛选"），每个问题的验收标准写清楚回答里要有什么（可选方案的对比、影响的模块和功能、工作量和风险、推荐和理由）。范围写明只做评估、不改代码，以及评估的结论用来做什么决定。可以省略"主流程""权限与数据"等与评估无关的章节。

项目有多个模块或多个仓库（例如前端和后端）时，在"范围"中写明这次涉及哪些模块；只改一边、需要参考另一边的，写明参考哪个仓库的什么（例如"后端已有的登录接口"）。

## 自查

写完后逐项检查，发现问题就改：

- 每条 FR 至少有一条可以实际检查的 AC，每条 AC 至少有一组具体的输入和期望输出
- 异常和边界情况都有对应的 AC，而不是只有正常流程
- 没有"快速""友好""合理"这类无法检查的词，除非给出了具体标准
- 各条需求之间没有互相矛盾
- "测试与验证"一节写明了测试数据和验证环境（快速档可以只写一句）
- "待确认问题"一节为空。不为空就回去问

## 确认

1. 给需求方一份 10 行以内的摘要：会做什么、不做什么、有哪些假设需要他们知情、他们之后会怎么验收。告诉他们完整文件的位置，愿意的话可以直接打开看。
2. 请他们确认。提出修改时，回到访谈，改完再自查、再确认。
3. 确认后，把顶部改为 `- 状态：已确认（<日期>）`。没有确认的 spec 不要标为"已确认"。
4. 如果是 git 仓库，把功能目录、`GLOSSARY.md` 和 `docs/adr/` 中本次的改动提交到当前分支。只提交这些文件，不 push。提交信息例如 `docs(<功能目录名>): 需求说明已确认`。
