# 只做这个需求

**不顺手重构、不升级无关依赖、不改无关文件。**

## 为什么

无关的改动会让评审变难、让风险变大，也会让需求方无法判断"这次到底改了什么"。一个需求的提交应该能单独审阅、单独回退。

## 例子

好的做法：

"发现 utils/date.ts 中有一个与本需求无关的时区隐患，已记入报告的'经验与改进建议'，未修改。"

不好的做法：

"顺便把整个 utils 目录改成了新的写法，并升级了日期库。"

## 常见借口

- **"反正都在改这个文件。"** 只改与需求相关的部分。整理代码可以作为单独的需求提出。
- **"升级依赖能修好一个警告。"** 与本需求无关就不升级，把警告记下来。

## 用在哪里

方案设计、代码实现、评审问题修复、缺陷修复；聊天中一个对话只处理一个需求。
