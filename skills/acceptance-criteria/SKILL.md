# 验收标准

验收标准（AC）是需求方验收、流水线验证和测试同事编写用例的共同依据。写到一个没参加过对话的人也能据此判断"通过还是不通过"的程度。

## 格式

每条 AC 有编号 `AC-<FR 编号>.<序号>`，例如 FR-2 的第一条是 `AC-2.1`。写成三段：

```markdown
- **AC-2.1** <一句话标题>
  - 前置条件：<数据、账号、环境、开关等起始状态>
  - 操作：<用户做了什么，或调用了什么接口、执行了什么命令>
  - 预期结果：<应该看到什么。具体到页面上的文字、接口返回的字段和值、数据的变化>
```

简单的 AC 可以写成一句话："在<什么情况>下，当<做了什么>，应该<看到什么>。"只要三个要素都在。

## 要求

- **可检查。** 不用"快速""友好""合理""正常"这类词，除非给出具体标准（"3 秒内返回""错误提示为'验证码已过期，请重新获取'"）。
- **每条 FR 至少一条 AC。** 并且不只写正常流程：输入不合法、权限不足、重复操作、边界值、依赖不可用，凡是访谈中谈到的都要有对应的 AC。
- **一条 AC 只检查一件事。** 一条里出现"并且……并且……"时，考虑拆开。
- **写明测试数据。** 需要特定数据或账号时，在前置条件里写清楚；访谈中定下的测试账号、测试环境也写进来。
- **写明怎么验证（可选）。** 已知可以用命令或接口验证的，写出来，例如"`GET /api/orders?status=paid` 返回的列表中不包含已退款订单"。这方便流水线和测试同事直接复用。
- **不写实现。** AC 描述可观察的行为，不描述代码怎么写。

## 例子

```markdown
### FR-2 验证码登录（优先级：必须有）

- **AC-2.1** 正确的验证码可以登录
  - 前置条件：手机号 13800000001 已注册，已获取验证码 123456（5 分钟内）
  - 操作：在登录页输入手机号和验证码，点"登录"
  - 预期结果：进入首页，右上角显示该用户的昵称
- **AC-2.2** 验证码过期
  - 前置条件：同上，但验证码获取于 6 分钟前
  - 操作：输入该验证码登录
  - 预期结果：停留在登录页，提示"验证码已过期，请重新获取"，不进入首页
- **AC-2.3** 连续输错被锁定：同一手机号连续输错 3 次后，第 4 次无论对错都提示"尝试次数过多，请 5 分钟后再试"。
```

## 自查

- 每条 FR 都有 AC，异常和边界情况都有 AC
- 每条 AC 的预期结果都是能看到、能比较的东西
- 拿着 AC 的人不需要再问任何问题就能执行
