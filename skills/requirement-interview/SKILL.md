# 需求访谈

## 目标

把需求谈到"换一个人来做，也会做出同一个东西"的清晰程度。访谈的结果之后交给无人值守的开发流水线，流水线里没有人能再回头问，所以**现在没问清楚的地方，后面只能靠猜**。

## 对面是谁

需求方通常是测试、产品经理或项目经理：有一定技术背景，熟悉接口、字段、状态、测试用例、测试环境这些概念，但不读代码。据此：

- 可以直接用他们熟悉的概念提问，例如"这个接口失败时返回什么错误码""列表要不要按创建时间倒序"。
- 不问代码层面的选择（用哪个框架、怎么拆模块、同步还是异步）。这些由你决定，记入 spec 的"技术假设"。
- 他们往往最清楚异常流程、测试数据和环境，这些要重点问。

## 开口之前

1. 先读项目里已有的资料：`GLOSSARY.md`（术语表；较早的项目可能叫 `CONTEXT.md`）、`docs/adr/`（已做的决定）、`README`、`CLAUDE.md` / `AGENTS.md`、`.requirement-pipeline/project-notes.md`，以及与需求相关的代码和现有页面、接口。
2. 能从代码和文档里得到答案的事，不拿去问。可以说"我看到现在的列表是按创建时间倒序的，新功能沿用这个顺序，对吗？"，把发现变成一个确认题。

## 怎么问

**先听，再复述。** 请对方用自己的话把想要的东西讲一遍。用两三句话复述你的理解，确认后再往下问。

**一次只问一个问题。** 每个问题给 2–4 个选项，把你推荐的放在第一个并说明理由。环境里有选择题式的提问工具就用它，否则用带编号的文字选项。对方说"你定"时，采用推荐项，记为假设。

**问结果，不问手段。** 问"提交之后，谁应该在多久之内看到这条记录"，不问"要不要用消息队列"。

**技术限制翻译成可见后果。** 不说"这需要改表结构"，而说"这样做的话，以前的历史订单不会带上这个信息，只有新订单才有。可以接受吗？"

**用具体例子提问。** "张三周五下午 6 点提交了申请，审批人周一才上班，这期间张三看到的状态是什么？"比"审批超时怎么处理"更好回答。

**追问到目的。** 对方说"加一个导出按钮"时，问清楚导出之后拿去做什么。真正的需求常常是另一件事。

**主动问对方没想到的情况：**
- 出错和中断：输入不合法、提交到一半关掉、重复提交、依赖的服务不可用
- 反悔：能不能撤销、修改、删除，谁可以
- 权限：谁能看、谁能改、谁不能看
- 边界：数量上限、时间期限、空值、超长输入、并发
- 已有的数据和进行中的业务怎么办
- 测试：用什么测试数据、在哪个环境验证、有没有现成的测试账号或测试替身
- 这次明确不做什么

**每条需求都问"怎么算做对了"。** 要一个可以实际检查的答案，它会成为验收标准（写法见 `{{REQ_KIT_ROOT}}/skills/acceptance-criteria/SKILL.md`）。

**控制节奏。** 每谈完一个主题，用一两句话小结"已经定了什么、还剩什么"。对方的说法与现有文档或系统行为矛盾时，直接指出并请对方选择。

**区分"必须问"和"可以假设"。** 猜错会做出错误东西的，一定问；其余的按最合理的理解假设并记录（见原则 `principle-dont-block-on-humans`）。

## 边谈边记

在功能目录下维护 `alignment.md`，每定下一件事就追加一条，不要等到最后再回忆：

```markdown
## <主题>
- 问题：<问题>
- 结论：<定下来的答案>
- 理由 / 被否的选项：<一句话>
- 来源：需求方明确确认 / 需求方说"你定"（记为假设）/ 从现有代码或文档得出
```

**术语。** 出现新的业务或领域术语，或者发现同一个词在不同地方意思不同时，写入仓库根目录的 `GLOSSARY.md`（不存在就创建）：

```markdown
## <术语>
<在本项目中的确切含义。一两句话。>
- 不要与"<容易混淆的词>"混用：<区别>
```

项目里已有 `CONTEXT.md`（旧名）时，先读它；新增的术语仍写入 `GLOSSARY.md`，两者是否合并由开发同事决定。

**重要决定。** 影响以后很多需求、并且不容易推翻的决定（例如"订单号对外展示时一律脱敏"），在 `docs/adr/` 下新建一条记录：`<四位编号>-<英文短名>.md`，写明背景、决定、理由。不确定是否算重要时，不写。

## 什么时候可以结束

**快速档**：要改什么、改成什么样、不改什么、每条验收标准，都有了结论。

**标准档**：下面每一项都有了结论，或被明确标为"假设"或"本次不做"：

- 要解决的问题，以及做成之后怎么衡量
- 谁会用，在什么场景下用
- 主流程的每一步
- 规则（计算方式、状态变化、限制条件）
- 出错、反悔、权限、边界、已有数据
- 测试数据和验证环境
- 本次不做的范围
- 每条需求的验收标准
- 优先级：哪些必须有，哪些可以以后再说

还有只有需求方能回答、且答错会导致做错东西的问题时，继续问，不要带着它进入下一步。
