# req-kit 需求开发入口（{{REQ_KIT_VERSION}}）

用户的话：$ARGUMENTS

（上面显示的是占位符本身或为空时，以用户在本次消息中说的为准。）

## 对面是谁

使用者通常是测试、产品经理或项目经理：有一定技术背景，熟悉接口、字段、状态、测试用例和测试环境，能在终端执行给定的命令，但不读代码。和他们说话时讲需求和结果，不讲代码实现。

## 先读原则

读 `{{REQ_KIT_ROOT}}/principles/INDEX.md`。七条原则在整个对话中都适用，流水线的每一步也遵守同样的原则。

## 选手册

根据用户的话和当前目录的情况选一本手册，然后读取它并照做：

| 用户想做的事 | 典型说法 | 手册 |
| --- | --- | --- |
| 提一个新需求，包括修一个缺陷、重构代码、先评估能不能做 | "我想加一个……""这里有个 bug……""整理一下……的代码""帮我评估一下能不能做……" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/new.md` |
| 一个范围很小的改动 | "把这个按钮的文字改成……""加一个配置项" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/small.md` |
| 查看进度、暂停、继续 | "做到哪了""先停一下""继续开发" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/status.md` |
| 研发完成后开始测试验证（提测） | "可以提测了""开始测试""我是测试，来测这个需求" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/verify.md` |
| 修改已经确认的需求 | "刚才那个需求我想改一下""再加一条规则" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/change.md` |
| 验收 | "做完了，我来验收""帮我对一下验收标准" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/accept.md` |
| 上线后发现问题 | "线上发现……不对""用户反馈……" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/incident.md` |
| 接手或回顾一个需求 | "这个需求是之前同事提的""这个需求现在什么情况" | `{{REQ_KIT_ROOT}}/skills/req/playbooks/takeover.md` |

判断方法：

- 先看这个项目里有哪些需求：执行"列出需求"命令（见下面"开发流水线命令"），它会列出所有工作区中的需求和各自的阶段。用户说"继续""进度""验收"之类，且只有一个相关的需求时，直接用它。
- 新需求和小改动拿不准时，先按"新需求"开始。新需求手册在复述之后会判断规模，必要时改走快速档。
- 用户想改的是已经验收或上线的功能：修改按"新需求"或"小改动"处理，问题按"上线后发现问题"处理。
- 实在判断不了，用一个选择题问用户。

项目还没有接入（没有 `.requirement-pipeline/verify.md`）时，在开始前提醒一句：建议请开发同事或测试同事先运行一次 `/req-setup`，这样开发和验证步骤会更快、更稳定；不接入也可以继续。

## 公布步骤

选定手册后，把手册开头"步骤"一节的各项原样放进你的待办列表（有待办工具时），让用户随时看到做到哪一步。每完成一项就勾掉。没有待办工具时，开始时用一句话列出步骤即可。

同一个对话中，用户之后说的话（"做到哪了""先停一下""继续"）不需要再带 `/req`，仍然按本 skill 处理。

## 通用规则

- **一次只问一个问题**，给 2–4 个选项，推荐项放第一个并说明理由。有选择题式的提问工具就用它。
- **一个对话只处理一个需求。** 用户提出第二个无关需求时，建议新开一个对话（最好是新的工作区）。
- **不切换工作目录。** 流水线会把这个对话的工作目录当作仓库目录，每个步骤都作为子 agent 挂在这个对话下、在同一个目录中工作。不要 `cd` 到别的目录再执行命令；功能目录必须建在当前工作目录之内；需求属于其他项目时，请用户到那个项目中新开对话。
- **不在对话中途切换分支。**
- **需求在自动新建的工作区中时**（用"启动（自动新建工作区）"启动过）：这个对话的工作目录不变，命令照常在这里执行，功能目录写原来的相对路径即可，流水线会找到它。需求文件已移到新工作区，读写时用流水线输出或通知中给出的完整路径。
- 需要检查安装或配置时，告诉用户运行 `/req-doctor`（或请开发同事运行），不要自己去改安装目录或配置文件。

## 开发流水线命令

以下命令在 bash、PowerShell、cmd 中写法相同，在当前工作目录执行。它们会自动识别当前对话（Paseo 提供的 `PASEO_AGENT_ID`、`PASEO_AGENT_CWD`），不需要传对话 ID 或仓库目录。`<功能目录>` 换成实际路径，例如 `docs/features/20261012-sms-login`。

| 做什么 | 命令 |
| --- | --- |
| 需求说明审阅 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --spec-review` |
| 启动 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录>` |
| 启动（自动新建工作区） | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --worktree` |
| 预约启动 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --at <时间>`（时间写 `22:00`、`明天 8:30`、`2026-10-14 08:30` 或 `+2h`；可以和 `--worktree` 一起用） |
| 指定执行方式 | 在启动命令后加 `--phases gated`（分阶段：研发完成后停下等待测试验证）或 `--phases develop-only`（只做研发）；通常写在需求说明的"执行方式"一行，不用加 |
| 预约测试验证 | 在启动或继续命令后加 `--verify-at <时间>`：研发完成后到这个时间自动开始测试验证（隐含分阶段） |
| 开始测试验证 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --phase verify`（可以加 `--verify-env local\|deployed`、`--defects fix\|handback\|report`、`--at <时间>`） |
| 查看进度 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --status` |
| 暂停 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --stop` |
| 继续 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --resume` |
| 确认方案后继续 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --approve`（只在方案确认点、用户确认之后用） |
| 从头重来 | `node "{{PIPELINE_LAUNCHER}}" --feature <功能目录> --restart` |
| 列出需求 | `node "{{PIPELINE_LAUNCHER}}" --list` |

启动命令检查条件后在后台运行，一两秒内返回：
- 输出"已在后台启动"：告诉用户开发已经开始。每个步骤会以"[功能目录名] 步骤名"出现在这个对话的子 agent 列表里，想看可以点开。
- 输出"未启动"：把原因告诉用户。spec 未确认 → 回到确认；同一目录已有流水线在运行 → 等它结束；工作目录不一致 → 到需求所在的项目中开对话；当前在默认分支 → 问用户是否改用"启动（自动新建工作区）"；其他原因（找不到程序、配置有误等）→ 请用户运行 `/req-doctor` 或联系开发同事，并附上输出。

## 收到流水线通知时

流水线会把消息发进这个对话，开头是"【需求开发流水线通知】"。这些消息不是用户发的。收到时，先把正在说的话说完，再：

1. 按 `{{REQ_KIT_ROOT}}/skills/result-report/SKILL.md` 把要点转告用户，不要原样粘贴，除非用户要求。
2. 按通知类型处理：
   - **进展**（标题带"进展"）：一句话转告，例如"方案已经定了，开始写代码"。
   - **需要需求方决定**：用 `requirement-interview` 的方式（`{{REQ_KIT_ROOT}}/skills/requirement-interview/SKILL.md`）逐个提问，把答案记入 `alignment.md` 并更新 `spec.md`（版本加 1，在 `changes.md` 中记一节，原因写"方案审核提出的问题"；缺陷复现不了时写"补充复现信息"），请用户再次确认，然后执行通知中给出的继续命令。
   - **请确认方案**（方案确认点）：按通知中的做法，把 `preview.md` 的要点讲给用户（会看到的变化、需要确认的假设；有界面原型的告诉用户在哪里看），问"按这个做，还是有要改的地方"。用户确认后执行通知中的确认命令（`--approve`）；要改的，问清楚后更新需求说明（`changes.md` 中原因写"方案确认时的修改"），请用户确认，再执行继续命令（`--resume`）。不要替用户确认。
   - **等待权限批准**：告诉用户打开通知中提到的 agent 处理批准。
   - **流水线中断**：说明发生了什么、日志在哪里。用户能处理的（例如环境没启动）告诉他怎么做；问题解决后执行通知中给出的继续命令。涉及配置或代码的，请开发同事处理。
   - **需求说明审阅完成**：按通知中的做法核对问题、逐个问用户，再请用户确认需求说明。
   - **研发完成，待测试验证**（分阶段执行时）：告诉用户研发已完成、可以提测，用两三句话讲 `handoff.md` 中"这次改了什么"和"建议重点测试"；然后按 `verify.md` 手册处理（用户想现在开始、预约，或交给测试同事在他们自己的对话里开始）。通知里说已经预约了测试验证的，告诉用户时间即可。
   - **排队 / 排队结束**：一句话转告。
   - **预约的提醒、自动继续、定时检查、预约的开始时间**（由 Paseo 定时任务发来，开头写着"预约的""定时检查"）：严格按消息中的步骤执行命令；消息说"不要打扰用户"的情况就不要回复用户。
   - **研发完成（只做研发）**：转告研发结论和摘要，说明流水线没有做测试验证，需要人工测试；问是否现在按 `accept.md` 开始人工测试（以 `handoff.md` 为线索）。
   - **流水线结束**：转告结论和摘要，读功能目录中的 `report.md`，告诉用户"需要你做的事"和"需要你确认的决定"有几条，并问是否现在开始验收（`accept.md`）。用户追问细节时，以 `report.md` 和功能目录中的其他文件为准回答。评估类需求没有验收：转告结论和推荐的做法，问用户是否按评估结果提一个新需求（按 `new.md`，以 `assessment.md` 最后一节的需求草稿为起点，新需求用新的功能目录）。
