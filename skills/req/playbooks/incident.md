# 手册：上线后发现的问题

需求方报告已上线（或已合并）的功能有问题。把问题问清楚，关联到原来的需求，生成一份缺陷说明，按小改动的流程修复。

## 步骤

1. 判断紧急程度
2. 问清现象
3. 关联原需求
4. 写缺陷说明
5. 请需求方确认
6. 启动修复

## 1. 判断紧急程度

先问一个问题：这个问题现在是否正在影响真实用户或数据（例如无法登录、数据错误、资金相关）？

- **是**：告诉需求方立即联系开发同事或值班人员处理线上情况（回滚、关闭开关、临时修复），这些不在 req-kit 的范围内，流水线也不会碰生产环境。然后继续下面的步骤，为正式修复准备缺陷说明。
- **否**：继续。

## 2. 问清现象

按 `{{REQ_KIT_ROOT}}/skills/requirement-interview/SKILL.md` 的方式，一次一个问题，问清：

- 现象：看到了什么，预期是什么
- 复现步骤：在哪个环境、用什么账号或数据、做了什么操作；能否稳定复现
- 影响范围：哪些用户、多少数据、从什么时候开始
- 证据：截图、错误信息、日志片段、接口返回（请需求方提供；不要索要或记录生产凭据和个人敏感信息）

能在本地复现的，在当前工作区尝试复现，并告诉需求方结果。

## 3. 关联原需求

用 `start-pipeline --list` 和 `docs/features/` 找到相关的原需求，读它的 `spec.md`、`report.md` 和 `acceptance.md`：

- 原来的验收标准是否覆盖了这个情况？覆盖了但没做对，属于缺陷；没覆盖，可能是需求遗漏，告诉需求方这一点。
- 原需求在另一个工作区或已经合并：这次修复用新的工作区和新的功能目录，不改原来的功能目录。

## 4. 写缺陷说明

在新的工作区中（必要时先按 `new.md` 第 1 步建议新建 worktree），创建功能目录 `docs/features/<YYYYMMDD>-fix-<英文短名>/` 并执行 `/req` 中的"登记需求"命令，按 `{{REQ_KIT_ROOT}}/skills/spec-writing/SKILL.md` 写 `spec.md`：

- 顶部：`- 档位：快速`（涉及数据修复、权限或多个模块时用标准档）、`- 类型：缺陷`
- 背景：现象、影响范围、关联的原需求（功能目录和对应的 FR/AC 编号）
- 功能需求：修复后应有的行为
- 验收标准：至少一条复现步骤对应的 AC（修复前失败、修复后通过），加上相邻的不应受影响的行为
- 已有的错误数据是否需要修正：需要的话单独作为一条需求，并请需求方确认修正规则

## 5. 请需求方确认

给出摘要：问题是什么、修复后会怎样、怎么验证。确认后标记"已确认"；提交规则同 `new.md`：将在自动新建的工作区中修复的不提交（启动时流水线在新工作区中提交）。

## 6. 启动修复

问是否现在开始，同意后执行"启动"命令（对话在项目主目录时执行"启动（自动新建工作区）"命令）。告诉需求方：修复完成后照常验收（`accept.md`），验收通过后请开发同事合并上线。
