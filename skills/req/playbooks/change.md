# 手册：修改需求

需求方想改一个已经确认过的需求：加一条、删一条、改规则、改验收标准。无论流水线是否在运行都适用。

## 步骤

1. 找到需求并查看状态
2. 暂停流水线（如在运行）
3. 只谈变化的部分
4. 更新需求说明和变更记录
5. 请需求方确认
6. 继续开发

## 1. 找到需求并查看状态

按 `{{REQ_KIT_ROOT}}/skills/req/playbooks/status.md` 第 1 步找到功能目录，执行"查看进度"命令，知道现在在哪一步。

需求在另一个工作区（`--list` 的输出中"位置"不是当前工作区）时，告诉需求方到那个工作区的对话中修改，不要在这里改。

已经验收通过、甚至上线的需求，建议作为新需求提出（用 `new.md` 或 `small.md`），在新需求的背景中引用原需求，而不是改旧的 spec。

## 2. 暂停流水线（如在运行）

状态为"运行中"时，说明修改需求需要先暂停：当前步骤做到一半的工作不保留，已完成的步骤保留；改完后会从方案设计开始，在已有方案和代码的基础上只处理变化的部分。确认后执行"暂停"命令。

需求方只是想补充一个不影响已有内容的小细节、而且开发已接近完成时，可以提出另一种做法供选择：先让这次开发完成，再作为一个小改动单独提出。

## 3. 只谈变化的部分

先读 `spec.md`、`alignment.md` 和 `changes.md`（如有）。请需求方说要改什么，复述确认。然后按 `{{REQ_KIT_ROOT}}/skills/requirement-interview/SKILL.md` 的方式，只针对变化的部分提问：

- 改动影响哪些已有的 FR、AC、规则
- 新增或改动的部分的异常、边界、权限
- 与已确认内容有冲突的地方，请对方选择
- 改动后怎么算做对了（新的或修改后的 AC）

问答记入 `alignment.md`（新的小节，标明"第 N 版修改"）。

## 4. 更新需求说明和变更记录

- 改 `spec.md`：顶部"版本"加 1，"状态"改回 `- 状态：草稿`。保留已有编号：删除的需求注明"已取消（第 N 版）"而不是删掉编号；新增的接着往后编号。按 `{{REQ_KIT_ROOT}}/skills/spec-writing/SKILL.md` 的清单自查。
- 在 `changes.md` 末尾追加一节，格式见 `{{REQ_KIT_ROOT}}/contracts/feature-files.md`：变更内容、原因、对进度的影响、提出人。

## 5. 请需求方确认

给出变更摘要（改了什么、对进度的影响），确认后把状态改为 `- 状态：已确认（<日期>）`，提交 `spec.md`、`alignment.md`、`changes.md`。

## 6. 继续开发

- 之前已经启动过流水线：执行"继续"命令。流水线发现 spec 变了，会从方案设计开始，在已有方案和代码的基础上只处理变化的部分（通常比第一次快）。告诉需求方这一点。
- 还没有启动过：问是否现在开始，同意后执行"启动"命令。
