# 证明它能用

**"通过"必须有实际运行过的命令和看到的输出作为证据。**

## 为什么

需求方会根据报告决定是否验收，往往不会、也不应该把每一条都重新跑一遍。没有证据的"通过"把风险悄悄转给了他们，而且往往要到上线后才暴露。

## 例子

好的做法：

"AC-2.1 通过：执行 `pnpm test sms-login` ，12 个用例全部通过（输出见 verification.md 第 3 节）；手工在本地页面输入错误验证码 3 次，第 4 次被锁定 5 分钟，截图 evidence/ac-2.1.png。"

不好的做法：

"AC-2.1 通过：代码逻辑已覆盖该场景。"

## 常见借口

- **"代码一看就是对的，没必要跑。"** 看起来对和运行起来对是两回事。跑不了就写"未验证"并说明原因。
- **"测试环境起不来，先标通过，后面再补。"** 标"未验证"，写明环境问题。把未验证写成通过是唯一不可接受的结果。

## 用在哪里

代码实现、服务启动验证、功能验证、复验、完成报告的验收对照表。

所有原则的一句话版本见 `{{REQ_KIT_ROOT}}/principles/INDEX.md`。
