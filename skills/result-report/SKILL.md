# 结果说明

需求方（测试、产品、项目经理）要根据你的话做决定：是否验收、是否需要回答问题、是否找开发同事。说清楚，并且让他们能自己核对。

## 写法

1. **结论先行。** 第一句话就是结论：做到哪一步了、成没成、要不要他们做什么。
2. **分清三类。** 已验证（有运行证据）、未验证（说明原因）、有问题（现象和影响）。不要把未验证的说成完成。
3. **给出证据位置。** 结论来自哪个文件的哪一节，例如"验收对照表见 report.md 第 3 节""AC-2.1 的测试输出见 verification.md"。能用命令复核的，给出命令。
4. **讲需求和结果，不讲实现。** 可以说接口、字段、页面、测试用例；不说类名、函数名、提交号，除非对方问起。
5. **下一步具体到动作。** "请按 report.md 的验收对照表逐条试用，AC-3.2 需要用测试账号 B 登录"，而不是"请验收"。
6. **长度。** 进展一句话；状态两三句；完成或中断不超过 8 行，详细内容指向文件。

## 常见场景

- **进展通知**：一句话，例如"方案已经定了（审核 1 轮），开始写代码"。
- **查看进度**：现在在做什么、已完成哪些、进行了多久；有等待决定或遗留问题时一并说明。
- **中断**：在哪一步、原因、日志位置；对方能自己处理的（例如测试服务没启动）给出做法，否则建议找开发同事；处理后怎么继续。
- **完成**：结论（可以验收 / 有遗留问题 / 未完成），最重要的一两条遗留问题，需要他们确认的决定有几条，下一步做什么。
- **接手**：这个需求要做什么（一两句）、现在在哪个阶段、有哪些待决事项、接下来建议做什么。

## 数据来源

以文件为准，不凭记忆：

- 进度：`start-pipeline --status` 的输出、`progress.md`
- 结论和证据：`report.md`、`verification.md`、`code-review.md`
- 需要人确认的决定：`report.md` 的"需要你确认的决定"、`decisions.tsv` 中 `needs_human` 为 `yes` 的行
- 需求和变更：`spec.md`、`changes.md`；验收结果：`acceptance.md`
