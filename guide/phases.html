分阶段执行与提测 ​

研发和测试常常是两拨人、两个节奏：研发完成要"提测"，测试同事先部署测试环境、准备数据，再验证，或者干脆人工测试。req-kit 把第 3–11 步分成研发和测试验证两个阶段，中间一个闸口。

三种执行方式 ​

执行方式研发完成时适合
连续（默认）写好提测说明后直接进入测试验证本地就能验证的项目
分阶段停下来通知"研发完成，可以提测"，等人说"开始测试验证"或到预约的时间有专门测试、需要先部署测试环境
只做研发写提测说明和研发报告后结束，测试由人完成测试必须由人完成

标准档的需求在确定档位时，/req 会问执行方式（项目配置里定好了就不问），写进需求说明头部：- 执行方式：分阶段。团队可以在项目配置中统一设置：

json
{ "phases": { "mode": "gated" } }

提测说明 ​

研发阶段的最后一步写 handoff.md，三种方式都写：

  1. 这次改了什么（按功能需求列出，附分支和提交范围）
  2. 怎么跑起来（依赖、迁移、配置项、启动命令）
  3. 自测结果（测试、代码评审结论、哪些验收标准已有自动化测试）
  4. 建议重点测试（风险最高的验收标准、回归范围）
  5. 已知问题和未完成项
  6. 测试需要的准备（数据、账号、开关——只写在哪里取，不写口令）

开始测试验证 ​

收到"研发完成，可以提测"后，在对话中说"开始测试验证"。AI 会讲一遍提测说明，然后确定：

  • 在哪里验证：本地启动服务，或已部署的测试环境。后者需要和你一起写 test-env.md（地址、如何确认被测版本、账号和口令从哪里取、可用的测试数据）。
  • 发现缺陷怎么办：当场修复并复验；退回研发（只记录缺陷，回到研发阶段修复、经过代码评审后重新提测）；或只记录。

也可以预约：启动时加 --verify-at 22:00，研发完成后到时自动开始；或在开始命令后加 --at。

测试同事接手 ​

用"开发时自动新建工作区"开发的需求，研发完成后，测试同事可以在这个项目任何工作区的对话中输入：

text
/req 开始测试验证 sms-login

之后的通知发到测试同事的对话，步骤仍在需求自己的工作区中运行。研发阶段仍然只能从发起的对话操作。

相关配置 ​

配置默认作用
phases.modecontinuous执行方式：continuous / gated / develop-only
phases.verify.environmentlocaldeployed：对已部署的测试环境验证
phases.verify.agents{}测试阶段用的 agent，例如 { "reviewer": { "paseoProfile": "测试" } }
phases.verify.defectsfixfix / handback / report
phases.verify.serviceStartnull测试阶段是否做服务启动验证；null 按档位

设计决定见 ADR 0022。
